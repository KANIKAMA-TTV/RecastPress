## 1. 今回の選択肢

| 案 | 方針 | 主な影響 |
| --- | --- | --- |
| A（推奨） | 認可済みPHP管理・内部処理で、互換ホスト経由の`$wpdb`による編集用WPテーブル・許可済み独自テーブルの読取り／データ更新を認める | 既存プラグインのSQLを活用しやすい。操作権限・対象・資源・変更検知・公開前検証を契約化する必要がある |
| B | プラグインの直接SQLは許可せず、互換API経由の操作へ限定する | SQL依存プラグインは改修・代替が必要。APIの副作用や権限の検証は引き続き必要 |

今回の対象は読取りとデータ更新の許可方針。テーブル作成・変更・削除等の構造変更は別判断。Aでも全SQL・任意プラグインへの無条件互換を約束しない。

## 2. A案の実行境界（詳細案）

- PHPは既決どおり認可済み管理操作または内部ジョブで起動し、公開リクエストからは起動しない。
- 互換ホストが操作主体・対象サイト・処理コンテキストを確認する。編集用のWP互換領域と許可済み独自テーブルを対象にする。
- 公開世代の実体・有効世代ポインター、RecastPressのジョブ・OIDC・監査等の制御状態、他サイトのデータへ直接書き込める権限を渡さない。独自状態への正当な処理は能力別APIで扱う。
- DB管理者権限やホストのファイル操作権限を与えない。別接続による迂回を防ぐため、PHPから取得できる資格情報・接続先・OS権限を合わせて制限する。SQL文字列の検査だけで境界を保証しない。
- 書込みは編集用作業状態へ行い、影響範囲を把握・検証して公開世代を構築する。任意SQLを解釈すれば常に変更行を特定できるとはせず、変更監視と必要に応じた広い再照合を組み合わせる詳細を詰める。
- 検証失敗時は新しい公開世代へ切り替えない。キャッシュ全パージだけで公開データが更新されたとは扱わない。監視不成立時はR49に従う。

WP互換領域への書込み権限は、投稿・設定・ユーザー等の改変能力を持ち得る。インストールしたプラグインを信頼する範囲と、ジョブ単位／プラグイン単位の隔離は明示して設計する。同じPHPプロセスの共有資格情報だけでプラグインごとの完全な隔離を主張しない。

## 3. 後続の契約と試験

対応SQL・結果型・エラー、時間／件数／出力量の上限、トランザクションと接続管理、保存フック再入・他投稿変更、独自テーブルの許可登録、公開への抽出、監視・再照合を具体化する。未対応SQLを成功扱いせず、理由と対象機能への影響を診断する。

テーブル構造変更はプラグインの導入・更新・削除と合わせて別途協議する。MySQLとMariaDBにはDDL等による暗黙コミットがあるため、外側でトランザクションを開始すれば全処理を取り消せるという契約にはしない。[MySQL公式](https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html)、[MariaDB公式](https://mariadb.com/docs/server/reference/sql-statements/transactions/sql-statements-that-cause-an-implicit-commit)。これらの参照は対応DB版の決定ではない。

採用後に両DB・三配備環境で、許可した読取り／更新の比較、禁止領域・別接続からの迂回拒否、失敗後の公開世代維持、変更検知・キャッシュ停止、競合・中断を試験する計画を具体化する。今回はR要求・T試験IDを追加しない。
