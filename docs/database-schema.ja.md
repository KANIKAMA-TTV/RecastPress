# DBスキーマ方針の検討

決定日：2026-10-25／実装照合：2026-10-30（日本時間）。**D07-01はA案で決定（R58）**。編集用の正本をWP互換構造で保持し、独自状態と公開用データを別領域へ置く。固定参照DDL・raw reader／CASと所有DB試験は実装済みで、製品の永続job／公開状態・一般schema／SQL互換は未完了。

## 1. 決定の範囲

**追加決定（2026-10-26、D07-02・R59～R61）**：[コア内部のDB自動最適化と変更検知](database-auto-optimization.ja.md)を承認。WP互換DBを正本に保ち、内部の派生データ・自動索引とbinlog追跡を採用する。WPテーブルの列構造・エンジンを最適化のために変更せず、直接SQL許可はD08で別途判断する。対応版・監視要件等は詳細化が残る。専用fixtureの実装・観測と製品の常駐監視を区別する（冒頭と[DB開発](database-development.ja.md)参照）。

編集用の正本はWPコアのテーブル・列・値の意味を互換維持する。独自構造へ全面変換するB案は採用しない。MariaDB・MySQLの初回両対応、公開系の別プロセス、編集用資格情報の非付与、公開要求からのPHP非到達、検証済み公開世代の切替は既決事項として維持する。

## 2. 比較

| 案 | 編集用の正本 | 主な利点 | 主な負担 |
| --- | --- | --- | --- |
| A（採用） | WPコアのテーブル・列・値の意味を互換維持し、独自状態は別領域へ保持 | 移行時の変換と既存SQL・プラグインへの適合処理を抑えやすい | WP由来の構造上の制約が残り、公開用データとの整合管理が必要 |
| B | 独自構造へ変換し、WP API／必要なSQLへ変換層を用意 | 内部構造を製品に合わせて設計しやすい | 移行変換・逆変換・SQL互換層の設計と検証が増える |

Aの推奨は既存の互換性重視方針に基づく設計上の判断。性能向上、移行成功、任意プラグインの互換性を実測した結論ではない。

## 3. 採用した構成と詳細化する点

| 領域 | 内容と境界 |
| --- | --- |
| 編集用の正本 | 投稿、メタ、分類、ユーザー、設定、コメント等。移行元ID・参照・値表現・接頭辞を保持する方向。単一サイトの固定DDL12表は抽出済み。異なる元schema・legacy charset／collation等は対応契約と検証が残る |
| RecastPress独自状態 | ジョブ、outbox、公開世代管理、移行進捗、OIDC連携、監査、成果物情報等。WP互換テーブルへの独自列追加を前提とせず、権限を分けられる別領域へ保持 |
| 公開用データ | 公開に必要な検証済みデータと生成物。正本から作り公開世代として切替。下書き・認証情報・非公開設定を公開資格情報から参照できない構成 |

これは論理的な領域分離案。DBサーバー三台を要求せず、DB・テーブル・保存先の物理配置と資格情報は後続設計で詰める。WP側のrevisionとRecastPressの処理用改訂・ジョブ状態も区別する。

プラグイン独自テーブルは、診断・一覧化・保持／変換／未対応の説明を行う既存方針を維持する。全テーブルの無条件取込み・実行許可や、編集DBの全内容を公開領域へ複製する案にはしない。

## 4. 別途判断する事項

- D08：`$wpdb`の直接SQL、独自テーブルの作成・変更権限、DB直結、変更検知と公開反映。
- D07詳細：対応DB版、文字コード・照合順序・SQLモード、追加索引、異なる移行元スキーマへの対応。
- 保存・公開：PHP処理の作業状態、整合スナップショット、複数投稿の変更、独自テーブルから公開用データへの抽出方法。
- 移行・復旧：入力形式、最終差分、書込停止、元WPへの戻し方。構造が近くても無変換で戻せるとは保証しない。
- 本体更新：スキーマ変更ありの方式・停止条件。独自状態や公開用データの構造変更も含めて判定する。

## 5. 後続の検証

固定7.1.3の参照DDLは `compatibility/schema/reference.json` とSQLへ生成済み（wp_／utf8mb4の限定条件、参照DDL専用）。raw値と限定reader／writer、所有fixtureの既実測は[DB開発](database-development.ja.md)参照。DDL抽出を全WP保存意味論・任意元schemaの互換保証としない。T43で両DBのID／参照、シリアライズ値、未知メタ、権限、コメント状態を比較し、公開資格情報から下書き・秘密・管理状態を読めないことを確認する。失敗したPHP処理の結果を公開しないこと、変更とキャッシュ全パージの整合も既存の保存・公開試験と合わせて検証する。直接SQLの試験はD08の契約後に具体化する。これら製品経路全体の試験済みとはしない。Cookie本体変更後は旧DB証跡のsource bindingも古くなっており、全８modeの再実測は再開時に行う。

## 6. 根拠

公式の[`wpdb`資料](https://developer.wordpress.org/reference/classes/wpdb/)は、任意テーブルへのアクセスとSQL入力を扱うメソッドを説明している。[プラグインのテーブル作成資料](https://developer.wordpress.org/plugins/creating-tables-with-plugins/)は、メタ・options・独自テーブル、接頭辞、構造更新を説明している。このため、独自構造へ変える場合はAPI以外の依存も評価する必要があると判断する。

2026-10-25に参照した一般資料であり、互換基準7.1.3の固定アーカイブ照合やDDL抽出を代替しない。[判断記録](decisions.ja.md)と[詳細設計](design.ja.md)第6.1節に対応する。
