## 1. 決定した仕様

**ユーザー指定**：「全ユーザーに対し、SSOを標準機能とする。ただしデフォルトはオフ。」

**追加指定**：「MFAは実装しない。SSOはOIDCのみ。」。以前のOIDC先行・SAML後続案をそのまま採用したとは扱わない。

**追加指定**：「オフ、ユーザーが任意に導入可能、必須要求と３段階にする」「必須要求時は、既存ユーザーのパスワードログインは一度だけ許可する」。

| 項目 | 決定した扱い |
| --- | --- |
| 提供範囲 | 全ユーザー向けのSSOを初回の標準機能として提供。管理者だけに限定しない |
| 初期状態 | SSOはオフ。機能の提供と有効化を区別する |
| SSO方針 | オフ／ユーザーが任意に導入可能／必須要求の3段階 |
| 必須要求の移行例外 | 既存ユーザーのパスワードログインは各ユーザーにつき一度だけ許可し、OIDC連携手続きに限定。途中の再開・回復等は具体化 |
| 認証と権限 | SSOで認証されても、それだけで管理権限やPHP起動権限を付与しない |
| MFA | RecastPressにMFA機能を実装しない。必須／任意の再協議予定を残さない |
| SSO方式 | OIDCのみ。SAMLの実装・後続対応予定は採用しない |
| 実装境界 | 認証処理とSSOの応答処理はRustで実装し、公開起点のPHP非到達を維持 |

全ユーザー向けとは、役割によってSSOの利用資格を管理者だけへ限定しないという意味。通常のユーザー認証でSSOを必須にするかは3段階の設定に従う。匿名での公開閲覧へ一律のログインを強制したり、外部アカウントを無条件に登録・権限付与したりする決定ではない。

## 2. 有効化と基本認証の詳細案

SSOのサイト設定は初期offとし、認可された管理操作でOIDC接続先を設定・検証してから任意／必須要求へ変更する詳細案とする。offではSSOのログインを開始・成立させない。旧WPのSSOプラグインや設定を見つけても、移行しただけで有効化しない。設定診断と接続試験の入口は通常のSSOログインとは別の管理操作として契約化する。

off時の標準ログインは基準WPに沿ってRustで提供する。任意ではユーザーがSSO導入を選べ、標準ログインも利用可能。必須要求では通常の認証をOIDCとし、既存ユーザーだけに一度限りのパスワードログインを認める。緊急回復、外部認証基盤停止、設定変更時の既存セッションとトークン失効は別途決める。必須要求を理由に未設計の恒常的パスワード回避経路を作らない。

Rustの認証担当が外部応答を検証し、サイト内ユーザーとセッションへ対応付ける。管理操作は管理サービスで再度認可し、SSOの利用だけでPHP実行を認めない。認証担当のプロセス配置、秘密・トークンの保存と鍵更新、リダイレクト先・有効期限・応答の一回性・セッション境界を具体化する。外部通信はAI接続とは別のSSO用途として許可範囲を設計する。

アカウント連携、自動登録、既存ユーザーとの紐付け、ロール・グループ対応、削除・無効化、複数IdP、API・CLI認証、ログアウト連携の契約は未決。メール一致だけで既存アカウントへ自動連携したり、外部属性をそのまま管理者権限にしたりしない詳細案とする。[OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)を参照し、方式に応じた識別子・検証・本人による連携確認を定める。

SSOは認証の委任として扱い、RecastPress側にはMFAの登録・要素検証・強制・管理画面・MFA用回復を実装しない。外部IdPが自身の方針でMFAを使うことは禁止しないが、その設定代行やMFA強制・確認を製品要件へ追加しない。SSO成功をRecastPressでMFAを検証済みと表示しない。標準ログインやOIDCのアカウント回復は別途必要であり、MFA非実装を理由に省略しない。

## 3. SSO対応方式（D06-04、OIDCのみで決定）

**決定（2026-10-25）**：ユーザーが「SSOはOIDCのみ」と指定。OIDCだけを提供対象とし、SAMLは後続対応にも採用しない。以前のA「OIDC先行、SAML後続」と異なる指定として記録する。全ユーザー向け標準提供・初期offは維持。[OpenID Foundation](https://openid.net/developers/how-connect-works/)、[OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)を参照してOIDCの契約を具体化する。

| 項目 | 残る具体化 |
| --- | --- |
| OIDCの認証フロー | 使用するフローとライブラリ、応答の検証、要求との対応・再利用拒否、秘密・鍵の管理 |
| 接続先とユーザー | IdP製品と接続先、複数IdPの範囲、登録・連携・権限対応・ログアウト・失効 |

方式以外の上記詳細は未決。外部サービス契約・実接続・資格情報の登録は行っていない。既存WPのSAML設定等を見つけた場合は未対応として診断し、OIDCへ自動変換したり、移行を検証済みとしたりしない。

## 4. SSOの3段階と一度限りの移行ログイン（D06-05・06、決定）

**決定（2026-10-25）**：ユーザー指定により3段階（R38）を採用し、さらに必須要求時の既存ユーザーのパスワードログインを一度だけ許可する（R39）。以前の併用／OIDC限定の二択への回答とはせず、この条件を現在の仕様とする。

| モード | 通常のログイン |
| --- | --- |
| オフ（初期値） | OIDCによるログインは利用不可。WPに沿う標準ログインを提供 |
| ユーザーが任意に導入可能 | ユーザーがOIDC導入を選択でき、標準ログインも利用可能 |
| 必須要求 | 通常はOIDCを要求。既存ユーザーは移行のためパスワードログインを一度だけ利用可能 |

一度限りの許可はユーザー単位にサーバーへ永続記録し、同時要求で複数回成立させない詳細案。失敗したパスワード試行を成功したログインと数えない。許可の消費とセッション発行を一貫して扱い、ブラウザーを変えても回数を増やせないようにする。

「既存」の判定時点、既にOIDC連携済みのユーザー、採用した期限内再開の詳細、セッション期限、消費する具体的時点、モード変更時の既存セッションと一度限りの許可の扱い、バックアップ復元時の整合性は未確定。連携失敗やオフ→必須の切替で自動的に許可を再発行する仕様は採用していない。IdP停止・紛失等の回復も別途決める。MFA非実装・OIDC限定・初期offは維持。

## 5. 一度限りのログインの利用範囲（D06-07、連携手続き専用で決定）

**決定（2026-10-25）**：ユーザーがA「OIDC連携手続きだけに限定」を採用。R41へ反映。以下は比較履歴。

| 選択肢 | パスワードで一度ログインした直後の扱い |
| --- | --- |
| A：OIDC連携手続きに限定（推奨案） | 連携画面・必要な確認だけを利用できる。OIDCでの本人確認と連携完了後に通常機能へ進む |
| B：通常機能も一度利用可能 | 既存の権限範囲で通常のログインセッションを発行。次回からOIDCを要求する。セッション期限・連携への誘導を詳細化 |

パスワード認証後に発行するのはOIDC連携専用の制限セッションとし、通常のログインセッションを発行しない。連携開始・必要な確認・OIDC応答の検証・本人による連携確定など、手続きに必要な操作だけを許可する。記事編集・一般の設定変更・通常のユーザー向け操作・PHP起動へ到達させない。画面を隠すだけでなくサーバー側の認可で拒否する。

OIDCでの本人確認と既存ユーザーへの連携が確定してから、元のユーザー権限に従う通常セッションへ切り替える。詳細案ではセッション識別子を更新し、手続き用セッションを失効させる。メール一致だけでの連携や外部属性による権限昇格を認めない。連携失敗・未完了・不正応答で通常セッションを発行しない。消費する具体的時点や中断・期限切れ・回復は残件とする。

## 6. 連携中断時の再開方針（D06-08、有効期限内の再開で決定）

**決定（2026-10-25）**：ユーザーがA「手続き用セッションの有効期限内は再開可能」を採用（R44）。同じユーザーの有効な連携専用セッション内で手続きを再開できる。以下は比較履歴。

| 選択肢 | 一度のパスワード認証後にOIDC連携を中断・失敗した場合 |
| --- | --- |
| A：有効な手続き用セッション内で再開可能（推奨案） | 有効期限内は同じユーザーの連携手続きを再開可能。失効・紛失後は管理者等による別途定める回復へ。パスワードログインの許可は自動再発行しない |
| B：中断・失敗後は回復手続きへ | 手続き用セッションが残っていても再開を許可せず、管理者等による回復を必要とする。中断と失敗の判定条件は具体化 |

再開は新たなパスワードログインの許可ではなく、既存の制限セッションで行う。失効・紛失後は別途定める回復へ進み、パスワードによる許可を自動再発行しない。再開しても通常機能の権限を与えず、OIDC本人確認・連携確定後に通常セッションへ移る。詳細案では再開時に新しいOIDCトランザクションを作り、古い応答等を再利用しない。セッションの具体的な有効期限、延長条件、許可の消費時点、回復の権限・本人確認・監査は未確定。
