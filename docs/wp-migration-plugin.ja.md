# WordPress側の対話型移行プラグインと仲介サービスの検討

更新日：2026-10-25（日本時間）。元WP用PHP製対話型プラグインと、直接転送・ファイル書出しの両対応は決定済み。以下の画面・通信・権限・受入契約は設計案。仲介サービスは必要性の検証まで採用を保留し、検討課題として維持する。

## 1. 役割分担

| 担当 | 役割 |
| --- | --- |
| 元WordPress上のPHPプラグイン | 管理画面での案内、環境・互換性診断、データとコードの取得、転送または書出し、進捗・再開、切替準備と後片付け |
| 利用者と自身の契約AI | テーマ・functions.phpをRustへ変換し、診断に応じて修正 |
| RecastPressの管理・移行機能 | データ取込み、Rustソースの隔離ビルド・Wasm検証、プレビュー・比較、公開準備、復旧計画 |
| 仲介サービス（未採用） | 必要に応じて案内・進行管理・接続支援・データ中継を担うか検討 |

プラグインの「対話型」は、管理者が画面上で選択・確認しながら進めるウィザードを基本案とする。最初に公開時PHP禁止、テーマ・functions.php移植の利用者責任、問い合わせフォーム分離、個別サポートのない提供形態、テスト支援が移行成功を保証しないことを説明する。AI接続は製品経路に追加しない。元WP側でPHPを使うことは、本番RecastPressの公開閲覧・公開APIからPHPを起動しないR06とは別の境界である。

移行診断は問い合わせフォームの利用と公開時PHPへの依存を検出し、移行後も同じフォームがCMS内で動くと案内しない。D23-01によりTallyを第一推奨、独自デザイン向けにWeb3Formsを代替候補として、プラグイン不要のリンク・埋込み・外部送信への置換を案内する。本体は問い合わせ受付・配送・保管を持たず、サービス契約・設定・データ管理は利用者が担う。既存問い合わせデータの扱いは未決。[外部フォーム推奨](external-forms.ja.md)と[対象サイトと提供方針](target-sites.ja.md)を参照。

元ホストにRustコンパイラー、SSH、DBダンプ用シェルがあることを必須にしない案とする。プラグインが使えるWP・PHP・DBの最低版は未決であり、移植先の互換基準7.1.3と同じ版に限定しない。

診断は親子テーマ、functions.phpから読み込むファイル、フック、依存プラグイン、独自投稿型等を列挙し、移植・分離が必要な箇所と未確認を区別する。静的な列挙が動的依存を網羅したとは表示しない。代表URLを自動抽出し、運用者が重要なページ・操作を追加する。元WPの画面・HTTP応答を初回診断時に記録し、移植用とテスト用のプロンプトに使う。最終同期後の切替直前にも記録し直して最終比較の基準とする。画面取得の実行方式は未決であり、元ホストにブラウザー実行環境を必須にしない。

## 2. 対話の流れ

| 段階 | 画面で扱う内容 | 実行・停止条件 |
| --- | --- | --- |
| 方針説明・診断 | 製品方針と利用者責任を説明。WP・PHP・DB、テーマ・子テーマ・functions.php、プラグイン、データ量、URL、ホスト制約、移植・確認作業を表示 | 不足情報とマルチサイトを検出し、未確認を成功扱いしない |
| 計画 | 対応可能／要修正／未対応、転送対象、必要容量、後続操作を提示 | 未対応や公開時PHP依存を隠して一括成功にしない |
| 独自機能の初期設定 | キャッシュの初期オン、SSOの3段階と初期オフ、自動更新支援等の設定希望を質問 | 回答を計画へ保存。移行先環境での検証・適用状態と分け、未確定項目を黙って採用しない |
| 初回の比較基準 | 代表ページの画面・HTTP応答を記録し、運用者が重要なページ・操作を追加 | 取得できない箇所は未確認。秘密・個人情報をAI資料へ既定で含めない |
| 移植・テスト資料 | 対象コード・SDK資料・依存一覧・移植用とテスト用のプロンプトを利用者が確認して取得 | 元サイトの記録を期待結果に使い、移植後の実装から正解を推測しない。プラグインがAIへ送信しない |
| 移植待ち | Rust移植と修正の進捗を保存 | 利用者の作業を待ち、期限経過を成功としない。ビルドはRecastPress側の隔離環境で行う |
| 接続・取得 | 移行先、対象データ、方式、認証済み接続を確認 | 元・先の管理権限を照合し、接続試験だけではデータ転送を始めない案 |
| 転送・取込み | チャンクごとの進捗、再試行、容量・不一致を表示 | ハッシュ、対象版、受領確認、再開地点を保存。重複取込みを防ぐ |
| 比較・プレビュー | URL・表示・検索・編集・公開操作の差分と未確認を表示 | WordPress側の記録と移行先を対応付ける。テスト通過をサイト移行成功保証と表示しない |
| 最終同期・切替準備 | 最終同期後の元サイトの画面・HTTP応答を再記録し、差分、バックアップ、DNS／プロキシ変更案を提示 | 最終テストの基準を更新。移植結果の確認と公開判断は利用者または委託先が担う。停止時間・切替方法はD12で決定 |
| 観察・終了 | エラー・復旧手順・残る作業、一時ファイル・移行資格情報の後片付け | 元サイト削除やDNS自動変更を導入だけで許可されたとは扱わない |

段階の並行実行可否は詳細設計で定める。プラグイン側と移行先でmigration_id・操作ID・状態・資料版を共有する案とし、ブラウザー終了後も再表示・再開できるようにする。

### 2.1 独自機能の初期設定（D16-02・R51、質問工程を採用）

**決定（2026-10-25）**：ユーザーの「追加機能の設定は、移行アシスタント機能の中で設定を聞く」を採用。移行アシスタントが独自機能の設定を質問し、回答を移行計画に含める。移行後はWP管理画面の追加1画面から同じ設定を変更できる。キャッシュは初期オン（R50）、SSOは初期オフ、MFAは実装しないという既決値を維持する。

| 質問する設定の案 | 既決値と残る扱い |
| --- | --- |
| キャッシュ | 初期オン・容量完全自動・TTLなし保持を表示し、利用希望を確認。R52により容量の数値・手動上限を質問しない。設定値と容量／監視等による実際の利用可否を分ける |
| SSO | 初期オフとOIDC限定を表示し、オフ／ユーザー任意／必須要求を質問。接続先の入力・検証、必須時の一度の連携用パスワード認証と期限内再開も案内 |
| 自動更新支援 | RecastPress本体の更新設定を質問。OS・Docker・DB・PHP等は操作説明・セットアップ支援のみで更新を実行しない。セキュリティ更新の配信状態を診断し、終了版には強く警告する。初期オン／オフ等の未決値は推測しない |
| その他の独自設定 | 診断結果と採用構成に必要な項目を共通設定定義から提示し、詳細は今後具体化 |

詳細案では「質問・下書き保存→移行先での入力／互換・権限・環境検証→選択値と実効状態の確認→適用」の状態を分ける。元WP上で回答しただけで本番設定を直ちに切り替えない。移行先の監視不成立時は、キャッシュ設定がオンでもR49に従い停止する。OIDC必須化等は接続・既存管理ユーザーの連携／回復経路を確認する工程と分け、途中失敗を成功扱いしない。

回答には設定定義の版・migration_id・対象環境・選択元・検証／適用結果を記録し、再開で回答を無条件に初期化・再適用しない。設定変更や移行先構成の変更があれば、影響する検証をやり直す。元WPのコメント設定等を引き継ぐ既決の移行ルールとも区別し、無関係な設定を上書きしない。

OIDC・SMTP・クラウド等の秘密は回答の通常ログ・AI向け資料へ含めず、必要な場合は移行先の認可済み入口で別に入力・保存する詳細案。元ホストへ移行先のOS／DB管理権限を渡さない。具体的な質問項目・入力方式・保存形式・適用タイミングは未確定。T42で回答の保持・検証・適用・再開と移行後の追加1画面への反映を検証する。実装・試験は未着手。

## 3. データ・再開・元サイトの保護

長時間の単一HTTP要求を前提にせず、件数・バイト数・時間を制限した分割処理とする案。認証済み管理操作または明示した内部実行から再開し、匿名訪問や訪問者起点のWP-Cronを移行処理の起動条件にしない。

manifest_version、migration_id、source_site_id、取得範囲、元WP版、取得時点、チャンク一覧・件数・ハッシュ、削除の扱い、再開地点をマニフェストに記録する。更新時刻だけで差分完全性を保証しない。初期取得中の編集、削除、メディア変更、外部プラグインの書込みをどう固定・再同期するかはD12の判断を残す。

通常の診断・取得で元コンテンツを書き換えない。移行状態の保存・一時ファイル作成と、コンテンツ凍結・設定変更・切替を別の操作にする。未知のテーブルやシリアライズ値を黙って落とさず、保持・変換・未対応を列挙する。D07-01・R58で移行先の編集用正本はWP互換構造維持に決定。[DBスキーマ方針](database-schema.ja.md)に従う。全DB取得と共通形式の論理エクスポートの選択、独自テーブルの適用、異なる移行元版の変換は別途決める。

AI向けコード資料と、本番コンテンツ・ユーザー情報・設定の移行データを別に扱う。パスワードハッシュや秘密値の移行範囲はD13と連携し、APIキー・SMTP等を移行先で無条件に再有効化しない。

## 4. 認証・公開境界の詳細案

管理者のログインと操作能力を要求ごとに検査する。画面を隠すだけでは権限検査にしない。ブラウザーからの状態変更にはCSRF対策を行い、WordPress nonceだけを認証・認可・再送防止の仕組みにしない。[Capabilities](https://developer.wordpress.org/plugins/security/checking-user-capabilities/)、[Nonces](https://developer.wordpress.org/apis/security/nonces/)

転送方式を採用する場合、元サイト・移行先・migration_id・操作範囲を結び付けた短期資格情報を使う案とする。再発行・失効・完了後の停止を定義し、移行先のDB・クラウド管理資格情報をWP側へ渡さない。接続文字列・資格情報・ユーザーデータをURLや通常ログへ記録しない。

移行先URLのHTTPS、接続先の所有確認、転送先・リダイレクトの検査を設計する。任意URLへの通信はSSRF対策を持つWordPress HTTP APIを基礎候補とし、ローカル・プライベート移行先を許容する場合の接続設計を別途決める。安全検査を一律無効化する方式にはしない。[wp_safe_remote_post](https://developer.wordpress.org/reference/functions/wp_safe_remote_post/)

一時エクスポートはWebの静的公開パスへ放置せず、認可済みダウンロードと期限・失効・削除を定義する。公開不能な保存領域が用意できなければ停止または代替方式を提示する案。非公開APIを使う場合も全エンドポイントで権限コールバックと対象・入力検査を行う。[Custom Endpoints](https://developer.wordpress.org/rest-api/extending-the-rest-api/adding-custom-endpoints/)

## 5. 転送方式（D16-01、両対応で決定）

**決定（2026-10-25）**：ユーザーがAを選択し、直接転送とファイル書出しの両方を提供する。以下は比較履歴。仲介サービスの採用はこの回答に含めない。

| 選択肢 | 利用方法・検証の違い |
| --- | --- |
| A：直接転送とファイル書出しの両方（推奨案） | 接続できる移行先へ認証付きで転送し、接続制約がある場合は書き出した移行パッケージを利用者が取り込む。両方式の同等性・再開・容量・秘密の検証が必要 |
| B：ファイル書出しを先行 | 利用者が移行パッケージを取得し、RecastPress側へ取り込む。直接転送は後続対応 |
| C：直接転送を先行 | 接続・認証済みの移行先へ転送。元ホストから到達できない場合の移行は、別経路が用意されるまで制約となる |

両方式とも、未知のPHPコードを移行先の公開ディレクトリへそのまま配置しない。プラグインは転送可否・不足容量・再開可否を明示する。

### 5.1 共通の移行単位（詳細案）

同じ移行計画・マニフェスト・論理チャンクを用い、直接転送は認証付き受信API、ファイル方式は移行先への取込みから、同じ検証・インポート処理へ接続する。チャンク形式、圧縮、暗号化、分割容量は未決。ファイル方式で巨大な一ファイルを必須にせず、元ホストの上限に合わせた分割を検討する。

直接転送では元WPから確認済み移行先の受信口へ送る案とし、移行先に元WPの管理パスワードを渡してクロールさせない。ファイル方式では利用者が認可済み画面から取得し、移行先の管理機能へ取り込む。AI向け移植資料と本番データの移行パッケージは別に管理する。

### 5.2 再開と方式の切替（詳細案）

受信側がmigration_id、資料版、チャンクID、ハッシュ、取込み状態を永続化して受領確認を返す。元側は受領が未確認なら照会・再送できるが、同じチャンクの再送で二重登録しない。途中失敗を理由に受入検査を省略しない。

直接転送からファイル方式へ移る場合も、同じ取得データ集合とマニフェストであることを照合する。元データが変わったら再取得・差分計画をやり直し、異なる時点のチャンクを混ぜない。接続失敗だけで自動的に機密データを書き出さず、画面で代替経路と保存先・容量を提示する案とする。

両方式の共通合格条件は件数・参照・メディアハッシュ・削除の整合性と同じ検証結果。直接方式では接続・権限・期限・再送、ファイル方式では改ざん・欠落・順序違い・重複・一時データの失効と削除も試験する。切替・最終同期の採否は、別途D12で決める。

## 6. 仲介サービスサイト（D17、必要性の検討）

**ユーザーからの追加検討課題**：「必要であれば、マイグレーション作業を仲介するサービスサイトを作る」。サービスの提供・実装・公開や、利用者データの預託は未決。

| サービスの役割案 | 何を扱うか | 追加の判断 |
| --- | --- | --- |
| 案内・進行管理 | 手順、診断結果の共有範囲、操作状態、接続の案内 | 保存するメタデータ、認証・利用者間分離、製品単体での代替経路 |
| データ中継・一時保管 | 移行パッケージやチャンクの中継、送達確認、再開 | 暗号化・鍵の管理主体、保持期間・削除、地域、容量・転送量、アクセス監査、料金 |
| 移行実行・配備支援 | データ取込み、隔離ビルド、比較検証、配備支援 | 実行責任、ホスト資格情報、テナント・コード隔離、障害・復旧・費用 |

まず、直接転送・ファイル方式では解決できない利用上の問題と、必要なサービスの役割を確認する。採用時はどの段階がサービス依存になるか、停止・終了時のデータ回収と自力移行経路を明示する。実データの中継・保存を、単に手順案内サイトを用意する判断へ混ぜない。

仲介サービスもAIへ接続する前提にはしない。利用者自身のAIによる変換を維持する。サービスへソース・実データ・資格情報を渡す範囲は別途決め、検討課題を追加しただけで外部転送を認可されたとは扱わない。

### 6.1 初回での位置づけ（D17-01、必要性検証まで保留で決定）

**決定（2026-10-25）**：ユーザーがAを選択。まず直接転送とファイル方式を具体化し、仲介サービスの採用は必要性を検証するまで保留する。以下は比較履歴。サービス案自体は検討課題として維持する。

| 選択肢 | 初回の設計と追加負担 |
| --- | --- |
| A：必要性の検証まで採用を保留（推奨案） | 直接転送・ファイル方式を先に具体化し、それで解決できない導入・移行上の問題を確認してからサービスを判断する |
| B：案内・進行管理サイトを初回から用意 | 手順・接続案内・進捗等を扱う。保存するメタデータ、認証、製品との連携、運営費用を設計。移行データ本体の中継・保管は含めない |
| C：データ中継サービスも初回から用意 | データ中継・一時保管と送達・再開支援も対象。暗号化・鍵・保持・削除・利用者間分離・容量・費用を追加設計 |

仲介サイトのアカウントやサービス稼働を、初回のプラグイン移行の必須条件にはしない詳細案とする。再検討時は、直接転送・ファイル方式で不足する具体的な利用シナリオ、必要な役割、扱うデータ、費用・運営負担を記録する。接続不能時にファイル方式で解決できる場合も区別し、サービスの存在だけでデータ預託を既定にしない。

利用者の設定負担や中断・再開の問題が両方式で十分に解決できない場合は、案内支援だけで足りるか、データ中継・処理が必要かを再度協議する。採用・外部データ保管・AI実行・配備代行・資格情報預託は、この保留の回答から導かない。

## 7. 残る判断と受入試験案

両転送方式は決定済み。残る判断は元ホストのWP・PHP・DB最低版、必要な能力、共通データ形式、取得整合性、分割・容量上限、書込停止・最終同期、秘密・ユーザー移行、DNS切替支援、配布・対応リリース、仲介サービスの必要性と役割。

| ID | 検証内容 |
| --- | --- |
