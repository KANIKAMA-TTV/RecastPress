# コメントの受付・承認・初期設定

更新日：2026-10-25（日本時間）。D10-03〜D10-10の決定を反映。WP本体の標準仕様で統一し、コメント更新フィードもRustで初回対応する。標準項目の採否を繰り返さず仕様抽出・比較試験へ整理。[統一方針](wp-standard-policy.ja.md)を参照。個別APIの照合・送信基盤等の詳細は未完了。実装・試験は未着手。

## 1. 決定した仕様

**ユーザー指定（D10-05）**：「WPの仕様を踏襲。デフォルトはコメントできない」。

| 項目 | 方針 |
| --- | --- |
| 初回の機能 | 既存コメントの移行・Rust表示、新規コメント・返信のRust受付を用意 |
| RecastPressの初期設定 | 新規サイトのコメント受付既定値を無効にする。投稿で個別指定しない場合はサイトの既定値に従う |
| 有効化 | 認可された管理操作で設定し、WPに沿って投稿単位の受付状態・投稿条件を扱う |
| 有効時の承認 | WPのコメント設定に沿って承認要否・承認履歴・検査結果等を判定。全件手動承認だけへ固定しない |
| 既存コメント | 受付無効と既存コメントの非表示・削除を同一にしない。公開済みコメントは表示可能 |
| 移行元設定 | サイトの既定値、投稿ごとの受付状態、承認設定を引き継ぐ。取得不能・未対応を新規初期値で黙って置換しない |
| メール通知 | WP標準相当の管理者・記事著者向け通知をRustで初回提供。一般投稿者への返信購読は含めず、送信基盤・初期送信設定は別途決める |
| スパム関連の判定 | WP本体の標準設定、重複・連投、承認待ち・不許可の判定仕様へ準拠。独自の追加制限や外部サービスを一括採用しない |
| コメント更新フィード | サイト全体・記事ごとのRSS 2.0・AtomをWP標準に沿ってRustで初回提供 |
| 処理主体 | フォーム出力、受付・検査・管理・公開反映をRust／許可された移植Wasmで実装し、PHPへ到達させない |

機能を実装することと、初期設定で有効にすることを区別する。前の三案からAを選んだとは記録せず、このユーザー指定を現在の決定とする。

**提供意図（D29）**：コメント受付と通知はWP標準機能を使うサイトの移行に備えて提供する。RecastPressの通常利用でコメントを使うことは推奨しない。新規サイトの受付初期offと、移行元で明示された受付・承認設定を引き継ぐ方針は維持する。メール通知をパッケージに含めても、外部メールサーバーへの接続や配信成功は保証しない。設定不足・送信失敗を運用者が確認できるようにする。

## 2. WordPressとの意味対応

受付の可否と、受け付けたコメントを承認待ちにするかは別の判断。受付しない投稿を「承認待ちで保存」する動作へ置き換えない。WPの投稿ごとのcomment_statusとcomments_open相当、管理設定による投稿条件・承認判定を契約化する。[comments_open](https://developer.wordpress.org/reference/functions/comments_open/)、[wp_check_comment_data](https://developer.wordpress.org/reference/functions/wp_check_comment_data/)

公式Web参照のpopulate_optionsにはdefault_comment_statusがopenと記載されている。RecastPressの受付無効はユーザーが指定した初期値の差分として記録し、「WP本体の初期値が無効だから」という根拠にはしない。7.1.3の固定アーカイブによる照合は未実施。[populate_options](https://developer.wordpress.org/reference/functions/populate_options/)

サイト設定の「新規投稿の既定値」と、既存投稿に保存された受付状態を分ける。D10-06のA回答により、元WPのサイト設定と投稿ごとの受付状態・承認設定を引き継ぐ。移行後の新規投稿も、その移行サイトの既定値を使う。RecastPressの新規初期値で全既存投稿を一括無効化しない。

Rust側は、設定・投稿状態・投稿者条件・返信先・入力を受付時に再評価する。無効と判定したときはフォーム表示だけで制限せず、直接送信・返信・REST等からの受付も拒否し、コメントや通知・PHPジョブを作らない。受付拒否時のHTTP応答・案内文は互換契約で定める。

フォーム表示、条件分岐API、受付判定、既存コメント表示の結果を一致させる。WP標準フック・フィルターの効果と設定の関係も固定ソースと比較する。互換性と公開権限の競合を無視して常にfalse／trueにする実装にはしない。

## 3. 受付を有効にした場合の詳細化

受付条件、名前・メール、ログイン要求、記事単位の受付、古い記事の閉鎖、承認設定・履歴、内容検査等の関係を基準WPのソースと比較し、Rust API・設定へ対応付ける。[check_comment](https://developer.wordpress.org/reference/functions/check_comment/)、[wp_allow_comment](https://developer.wordpress.org/reference/functions/wp_allow_comment/)

承認履歴に使うメールアドレスや名前の一致を、本人認証の証明と混同しない。WPとの判定互換と、検証済みアカウント・メール等の本人確認は別に記録する。追加の制約を入れる場合は互換差分として明示する。

標準の設定項目・初期値、匿名／ログイン条件、HTML・リンク制限、連投・スパム関連判定は基準WP本体に沿って一覧化・照合する。RecastPressの新規サイト初期受付offは既定の差分として維持する。通知の送信条件・内容、編集・削除等の標準動作はD10-10で採用対象とし、照合・実現方式の詳細化が残る。送信基盤・反映時間の運用目標も具体化する。外部スパムサービスは含めない。コメントフィードはD10-09で採用し、トラックバック・ピンバック等の他のコア標準は全体の統一方針に従う。

## 4. 移行元の受付設定（D10-06、引継ぎで決定）

**決定（2026-10-25）**：ユーザーがAを選択。元WPのサイト・投稿ごとの受付設定と承認設定を引き継ぐ。以下は比較履歴。新規サイトの初期値offとは分ける。

| 選択肢 | 移行時の動作 |
| --- | --- |
| A：元WPの明示的な設定を引き継ぐ（推奨案） | サイト設定・投稿ごとの受付状態・承認設定を診断し、対応する設定を維持。欠落・不明・未対応は成功扱いせず確認し、未指定時にRecastPressの初期値を適用 |
| B：移行後も全投稿の新規受付を無効にして開始 | 元の設定を記録・提示したうえで、新規受付を無効化。利用者が確認して再有効化する。元サイトとの動作変更を明示 |

既存コメントの公開状態・表示はこの決定で変更しない。元WPで有効な設定は維持し、新規サイトの初期値offを上書き理由にしない。項目・投稿ID・取得値・元WP版・対応先・診断結果を記録し、サイト設定と投稿個別値の優先関係を比較する詳細案とする。

元サイトの保存値・実効値の取得を区別し、取得権限不足、値の不明、変換未対応を「指定なし」とみなして初期値へ置換しない。必要な承認履歴・投稿者参照・個人情報の保持範囲も別途契約化し、判定を再現できない場合は未解決と明示する。プラグイン独自の承認・スパム機能は標準設定の引継ぎだけで対応済みとはしない。

## 5. 管理者・記事著者向けメール通知（D10-07、初回対応で決定）

**決定（2026-10-25）**：ユーザーがAを選択。WP標準相当の管理者・記事著者向けコメント通知をRustで初回提供する。R29へ反映。以下の表は比較履歴。

| 選択肢 | 初回の範囲 |
| --- | --- |
| A：WP標準相当の通知をRustで用意（推奨案） | 設定に従い、承認待ちは管理者等、新規コメントは記事著者等へ通知する。宛先・送信条件は基準WPと比較し、送信先設定・SMTP等の準備が必要 |
| B：初回は管理画面での確認のみ | コメント状態を管理画面で確認し、メール通知は後続対応。移行元の通知設定がある場合は機能差分を明示 |

WPには承認待ちの管理者等への通知と記事著者等への通知がある。[wp_notify_moderator](https://developer.wordpress.org/reference/functions/wp_notify_moderator/)、[wp_notify_postauthor](https://developer.wordpress.org/reference/functions/wp_notify_postauthor/)。Aを採用。一般のコメント投稿者への返信購読メールや任意外部通知は、この一件に含めない。

詳細案は、コメント状態の確定とRust専用の通知要求を原子的に記録し、PHP用ワーカーを使わず送る構成。SMTP等が未設定なら送信せず、設定不足・失敗を管理画面へ返す。宛先は設定・権限・記事著者情報から解決し、投稿者が任意に指定した通知先へ送らない。送信条件・本文・個人情報の範囲・冪等キー・再試行・回数制限・送信基盤・初期送信設定は別途決める。

コメント保存の成功とメール到達は区別する。メール失敗だけでコメントを再登録・再公開せず、設定移行で元ホストのSMTP秘密情報を無条件に引き継いで送信開始しない案とする。

## 6. スパム対策の初回範囲（D10-08、WP本体準拠で決定）

**決定（2026-10-25）**：ユーザーが「WP本体の仕様に準拠。」と指定。初回のコメント検査・スパム関連判定を基準WP本体に準拠させ、Rustで実装する。R30へ反映。独自の追加制限を含む以前のA案を選択したとは記録しない。以下の表は比較履歴であり、採用仕様はこのユーザー指定とする。

レビューの公開書込みに伴う資源消費と、初回の利用者操作・外部副作用の範囲に対応する。WPの重複判定や承認判定を参照し、Rustでの標準設定・検査と追加サービスを区別する。[wp_allow_comment](https://developer.wordpress.org/reference/functions/wp_allow_comment/)、[check_comment](https://developer.wordpress.org/reference/functions/check_comment/)。公開Web資料は固定7.1.3ソースの照合完了を意味しない。

| 選択肢 | 初回の範囲と影響 |
| --- | --- |
| A：Rust内部の基本対策を先行（推奨案） | WP標準相当の設定・重複検査に加え、連投・入力サイズ・資源消費の制限を具体化。外部スパム判定サービス連携は後続対応 |
| B：基本対策と任意の外部サービス連携を初回提供 | Aに加え、管理者が設定して有効化する外部判定をRustから実行。サービス選定、送信データ、資格情報、費用・障害時の扱いを追加設計 |

準拠対象として、重複判定、連投判定、リンク数・モデレーション語句・不許可語句、承認履歴等を基準ソースから一覧化する。条件の評価順、閾値・初期値、権限による例外、対応するフック・フィルター、戻り値・エラーと状態遷移も比較する。不許可判定をすべてspamや承認待ちへ一律変換しない。[wp_allow_comment](https://developer.wordpress.org/reference/functions/wp_allow_comment/)、[check_comment](https://developer.wordpress.org/reference/functions/check_comment/)、[wp_check_comment_disallowed_list](https://developer.wordpress.org/reference/functions/wp_check_comment_disallowed_list/)、[wp_check_comment_flood](https://developer.wordpress.org/reference/functions/wp_check_comment_flood/)

閾値や例外はRecastPress独自に選び直さず、固定7.1.3ソースを照合して契約へ起こす。IP・メール等の必要な判定データと保持・閲覧権限を明示し、公開データへ含めない。フック相当はRust／移植Wasmの許可された経路で扱い、判定からPHPを呼ばない。外部スパム判定サービスやCAPTCHA、独自の追加制限は今回の採用に含めず、必要性と互換差分を別途判断する。HTTP・ホスト側の資源上限もWP準拠の判定と区別して記録する。既存の外部スパムプラグインの設定移行だけで、その機能を対応済みとはしない。

## 7. コメント更新フィード（D10-09、初回対応で決定）

**決定（2026-10-25）**：ユーザーが「WP本体の標準仕様で一貫して」と指定。標準コメント更新フィードをRustで初回提供し、R32へ反映。以下は比較履歴。D10-10・R31により標準機能全体の判断基準も統一した。

記事更新フィードR24とは別に、コメントを購読するRSS 2.0・AtomもR32で初回採用済み。基準WPのコメントフィード入口と標準テーマのリンク出力を参照する。[get_post_comments_feed_link](https://developer.wordpress.org/reference/functions/get_post_comments_feed_link/)、[do_feed_rss2](https://developer.wordpress.org/reference/functions/do_feed_rss2/)、[do_feed_atom](https://developer.wordpress.org/reference/functions/do_feed_atom/)

| 選択肢 | 初回の範囲と影響 |
| --- | --- |
| A：WP準拠のコメントフィードをRustで初回提供（推奨案） | サイト全体・記事ごとのRSS 2.0・Atomを提供。リンク・URL・配信内容と、承認・非公開化・削除後の更新を比較する |
| B：コメントフィードは後続対応 | 記事フィード・コメント表示と通知を先行。コメント購読URLの未対応を明示し、リンクだけで互換としない |

公開可能な記事・コメントだけを配信し、保留・スパム・ゴミ箱やメール・IP等を漏らさずPHPを使わない。受付無効と既存コメントの購読可否は区別する。件数・本文範囲等の標準仕様は基準WPと照合し、キャッシュ失効等の具体的実現方式も詳細化する。一般投稿者向け返信購読メールは含めない。トラックバック・ピンバック等の他のコア標準はD10-10の全体方針で扱う。

## 8. 検証計画

初期設定でフォーム・受付API・直接送信・返信・REST等が同じ受付不可判定となること、拒否時に保存・通知・PHP起動をしないこと、有効化後に選んだ設定どおり動くことを検証する。コア標準REST等はR31により採用対象であり、固定ソースに基づいて受入口の迂回試験へ含める。

既存コメントの表示維持、受付停止後の送信、設定変更と投稿状態の区別、承認状態の遷移、非公開データ・著者メール・IPの非露出、公開世代とキャッシュの整合性も比較する。D10-06に従い、移行前後のサイト既定値・投稿個別値・承認結果と移行後の新規投稿の既定値を照合し、取得不能・未対応・独自機能を検出する。

D10-07の通知は、基準WPに対応する設定・状態・宛先と抑止条件を比較する。テスト送信先を使い、未設定・停止・タイムアウト・再配送・状態変更と競合する場合も、PHP非到達とコメントの非重複を検証する。メールの重複送信や到達保証の限界も明示し、保存成功を送達確認として扱わない。これらは将来の試験計画であり、実施済みではない。

D10-08の検査は、重複・連投・語句・リンク数の境界値、権限例外、承認履歴、設定と判定順、状態遷移を固定WP環境と比較する。同時投稿でも検査の迂回や二重登録を起こさず、拒否時の通知・PHP実行が0であることを検証する。固定ソースの抽出・照合、試験データ作成と実行は未実施。

D10-09のコメントフィードはT27に対応する。サイト全体・記事単位、RSS 2.0・Atom、リンク・URL・標準設定・内容・更新を固定WPと比較し、非公開化・削除とキャッシュ、非公開データの非露出、PHP非到達を検証する。未実施。
