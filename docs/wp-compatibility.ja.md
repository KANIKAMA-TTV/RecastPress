## 1. 決定した基準

**決定（2026-10-25）**：WordPress 7.1.3を互換基準に固定し、その版に残る非推奨の標準テーマ用APIも対応対象に含める。開発中に新しいWordPressが公開されても基準を自動更新しない。

R15で決めた標準テーマ用API全体は、公式テンプレートタグだけでなく、クエリ・ループ・条件分岐・フック・設定・翻訳・エスケープ・資産管理等の必要な関数・クラス・状態を含む。初回のサイト構成はR20で単一サイト先行に決定した。

**追加決定（D10-10・R31）**：ユーザーの「WP本体の標準仕様で一貫して」により、コア標準機能・設定・APIの振る舞いを全体の基本仕様へ統一。公開REST等も標準に含まれる項目は採用対象として、固定ソース照合・契約・実装・比較試験へ整理し、機能の採否を再質問しない。既決の差分と実行制約、新たな衝突の扱いは[統一方針](wp-standard-policy.ja.md)に従う。

2026-10-25に公式リリース一覧と公開チェックサムを確認。7.1.3の公開日は2026-10-06。[公式リリース一覧](https://wordpress.org/download/releases/)

| 主参照アーカイブ | [wordpress-7.1.3.tar.gz](https://wordpress.org/wordpress-7.1.3.tar.gz) |

初期設計では公式公開値の確認までだったが、後続作業でアーカイブ取得・展開・SHA再計算と3,782file manifest作成を実施済み。記録は `.reference/wordpress-7.1.3/recastpress-reference.json` と参照取得ツールに保持する。参照物の同一性確認と、現Rust sourceへの互換証跡再生成は別である。GitのコミットIDは未確認のため記載せず、主参照は固定公式リリースアーカイブのまま。後でGit／SVN識別子を追加しても基準を黙って置き換えない。

実装時の取得手順では、アーカイブ照合に加えてSHA-256と取得情報を記録する案とする。zipとtar.gzのバイト列が異なることを理由に、異なるAPI基準として扱わない。展開後の対象ファイル一覧と内容ハッシュも記録して参照コーパスを固定する。

## 3. API母集合の確定方法

基準アーカイブのソースを一次資料とし、現在のWeb上のAPIリファレンスは補助資料とする。Web資料に新しい版の変更が反映されても、7.1.3の挙動を自動的に置き換えない。

| 手順 | 出力と確認事項 |
| --- | --- |
| 対象の列挙 | テンプレートタグと標準テーマ用APIの関数・クラス・メソッド・フック・必要な定数／状態を列挙 |
| 依存の展開 | 呼出し先、登録済み標準コールバック、クエリ・ループ・オプション・利用者への依存を追跡 |
| 適用条件の記録 | 公開／管理、単一／マルチサイト、プラグイン有無、要求段階、言語・データ条件を明示 |
| 意味の契約化 | 引数・戻り値・出力・型変換・参照・副作用・順序・診断の契約を記録 |
| SDKへの対応 | Rust SDKのAPIとWasmホスト呼出し、互換補助API、未対応点を記録 |
| 比較ケース | 7.1.3の参照実行とRust／Wasmの正常・境界・状態変化のケースを対応付け |

個別レコードは基準版、元ソース位置・ハッシュ、シンボル、適用条件、契約、SDK対応、比較ケース、状態、根拠を持つ。母集合件数と検証済み件数は抽出後に確定し、現在は未集計とする。

未対応API、未実装のホストAPI、未採用の製品機能を「空文字列を返す」「常にfalse」等で対応済みにしない。製品機能範囲が未決なら、APIの適用条件も未決として表示する。単一サイト先行は基準版の採用とは別の回答によって決定した。

## 4. 非推奨・旧API

| 区分 | 扱い |
| --- | --- |
| 7.1.3に存在する標準テーマ用API | 通常・非推奨を問わず互換対象へ含める |
| 非推奨APIの別名・ラッパー | 旧引数、戻り値、直接出力、呼出し先、必要な診断を比較し、単なる名前の対応で完了しない |
| 7.1.3より前に削除されたAPI | 移植診断で検出し、代替・追加互換層・個別対応を協議。黙って成功扱いしない |
| 7.1.3より後に追加・変更されたAPI | この基準の全対応へ自動的に含めない。新しい互換基準または追加プロファイルとして設計判断を記録 |
| テーマ・プラグイン独自API | 基準WPの母集合とは分け、利用者のAIによる移植と製品の比較検証で扱う |

非推奨の意味を保つことと、AIが書くRustソースで新しいAPIを使うことは両立できる。旧API呼出しの意味を維持して移植できる対応表を用意し、変更が生じる場合は利用者へ差分として示す。WordPressには非推奨呼出しの診断とフックがあるため、その観測も契約に含める。[公式_deprecated_function](https://developer.wordpress.org/reference/functions/_deprecated_function/)

## 5. 比較実行と基準変更

参照環境は7.1.3に固定し、PHP・DB・設定・データ・プラグイン・親子テーマ・タイムゾーン・言語もケースごとに記録する。PHPやDBの対応版は未決。参照環境は移行・試験用であり、本番コアには残さない。

通常の戻り値・HTML・副作用に加え、非推奨診断、フックの引数と順序、入れ子クエリ、空データ、Unicode、型境界、投稿更新後の結果を比較する。参照WordPress自体の不具合や危険な挙動をそのまま再現するかは個別に判断し、差分と理由を記録して互換実装と区別する。

基準変更は、新旧APIと挙動の差分、SDK・Wasm契約、移植済みテーマ、PHPプラグイン、DB・配備、再検証の影響を評価して明示的に行う。基準を固定していても、発見した修正事項を無視する意味にはしない。修正内容と互換差分を記録する。

## 6. 初回のサイト構成（単一サイト先行で決定）

**決定（2026-10-25）**：レビュー後の第1件にユーザーが「A」と回答。初回は単一サイトの導入・移行・運用を先行し、マルチサイトは後続対応とする。以下は比較履歴。マルチサイトは一つのWordPress設置で複数サイトを管理する機能であり、独立した複数設置とは異なる。[WordPress Multisite](https://developer.wordpress.org/advanced-administration/multisite/)

| 選択肢 | 初回の受入範囲と追加設計 |
| --- | --- |
| A：単一サイトを先行 | 単一サイトの導入・移行・運用を初回正式対象にする案。マルチサイト条件付きAPIの提供時期・適用条件をR15と整合させ、未対応を全対応として数えない |
| B：単一サイトとマルチサイトを初回から対象 | ネットワーク管理、共有ユーザー、サイト別権限・データ・資産、URL解決、サイト切替・復元、ネットワーク単位の移行・復旧も設計・検証 |

Wasm契約のsite_idはホストが確定する。マルチサイトのswitch_to_blog相当を提供する場合は、許可されたサイト集合、切替状態、元サイトへの復元、世代・キャッシュ分離を契約化する。固定site_idだからサイト切替を常に禁止するという仕様へ自動的に限定しない。元WordPressでもサイト切替は読み込んだテーマ・プラグインのコード切替とは別である。[switch_to_blog](https://developer.wordpress.org/reference/functions/switch_to_blog/)

R15の標準テーマ用API全体という目標は保持し、初回は単一サイトでの適用条件と結果を比較する。マルチサイト判定や単一サイト時の標準動作があるAPIを一律に除外しない。ネットワーク固有機能は後続対応とし、未提供・未検証を明記する。初回の対応率と将来の全体目標を分けて表示し、マルチサイト条件まで検証済みとはしない。

移行診断でマルチサイトを検出した場合、通常の単一サイト移行を成功扱いしない。ネットワークを複数の単一サイトへ変換する機能の採用や、後続リリースの時期は別途決める。
