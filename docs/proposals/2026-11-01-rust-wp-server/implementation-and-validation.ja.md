# RecastPress 新構成の実装順と受入条件案

作成日：2026-11-01（日本時間）  
版：0.5  
対応する実装の開始版：0.5.0  
位置付け：[概要設計案](README.ja.md)を実装と製品判断へ分解する計画

## 1 実装の進め方

新構成は文書v0.5・実装0.5.0から開始する。0.5.0への版切替は開始位置の指定であり、P0〜P7の達成を示さない。既存の独立実験は自身の試作版を維持し、依存する本体packageのlock上の版だけを実際のworkspaceへ合わせる。旧版の実測証跡は履歴として保持し、新版の検証成功へ付け替えない。

WP APIの件数を増やす順から、利用者の操作を通し、互換性を比較しながら高速化を追加する順へ変更する。初期段階はキャッシュと索引を止め、Rust入口、php-wasm、WP、DBの基準経路を先に成立させる。

各段階には、成果物、比較条件、停止して見直す条件を設ける。合格前に依存する最適化を重ねない。開発用の内部上限は試験入力として使えるが、製品管理者に手動キャッシュ容量を指定させる仕様へ転用しない。

中間マイルストーンを設けても、元案から引き継ぐ初回正式対応のMySQL／MariaDB、三配備先、標準機能、OIDC等を黙って削減しない。後続段階へ置くことと、初回リリースから外すことを区別する。

## 2 段階別の成果物

| 段階 | 実装するもの | 主な受入条件 |
| --- | --- | --- |
| P0 設計と基準の固定 | 責務、受入policy、WP・PHP・DB・host版、Rust直接実行の成立実証、代表サイト、依存、再利用判断 | Node.jsなしでPHPのWasm・ホスト呼出し・清掃が成立し、既存実装との差分が明らか |
| P1 動的な基準経路 | Rust HTTP、php-wasm、WP起動、テーマ・plugin、標準wpdb APIを満たすDB経路の実証 | キャッシュなしで代表操作が通常PHP環境と一致し、driver直接操作を拒否できる |
| P2 DB接続とオブジェクトキャッシュ | 正本DBの制御経路、DB session、WP cache API、要求内と共有の分離 | 値・状態・原子操作・transaction・要求分離が一致する |
| P3 変更追跡と自動容量 | 自身の書込み失効、snapshot・binlog、復帰、複数process、自動予算 | 追跡不能時に共有高速経路が停止し、DB通常経路へ戻れる |
| P4 応答キャッシュと受入制御 | 適格性、キー、全パージ、HTTP整合、拡張導入・更新拒否 | 公開更新・非公開化・競合・plugin衝突で誤共有しない |
| P5 内部索引 | 検証できる検索の派生データと限定的な高速経路 | SQL・WP挙動との同等性と実際の効果が確認できる |
| P6 製品操作と移行 | 独自設定、診断、OIDC、直接転送・file取込み、切替比較 | 一サイトの導入から編集・公開・移行まで操作で通る |
| P7 正式配備と継続運用 | 三環境、両DB、backup・復元、同梱基盤の更新・新旧切替 | 合意した性能・資源・反映期限・復旧目標を満たす |

P1から最低限の専有領域保護・衝突拒否を適用する。P4は製品用の診断と全導入経路を完成させる段階であり、それ以前に任意の第三者コードを本番受入れする意味ではない。

P1〜P2で基準経路の資源量を測り、P3で全体の自動配分へ接続する。内部索引・応答キャッシュの本番利用は、追跡・資源・失効条件の成立後とする。

P2のオブジェクト共有は、更新元と条件を管理した使い捨てfixtureで検証する。外部更新を含む製品構成での共有利用は、P3の変更追跡・停止・復帰条件が成立した後に有効化する。

## 3 段階ごとの具体的な合格条件

### 3.1 P0 設計と基準の固定

1. 代表サイトに、投稿・固定ページ・一覧・検索・media・ログイン・REST・コメント等の操作と期待結果を定める。
2. 通常PHPで動く比較WPと、php-wasmで動く対象WPのソース版・DBデータ・theme・plugin・設定を揃える。
3. DB互換方針A案の標準wpdb APIと拒否対象を固定し、接続候補1に必要なhost・RPC・DB機能、配布依存と実証環境を用意する。
4. 専有領域、独自SQL・DDL、未対応能力、判定保留の扱いを受入policyとして定める。
5. 既存コードで再利用する範囲のsourceと検証状態を確定する。旧証跡のhashだけを書き換えない。

実行ホストB案の成立確認をP0の通過条件とする。Node.jsを使わず、RustでホストしたPHPのWasmが、基本PHP、ファイル読込み、要求の入出力、RustへのDB・cache呼出し、要求終了・清掃・異常時の回収を実行できることを確認する。PHPビルド・Wasm engine・ABI・追加runtime依存を実物で固定する。成立しなければP1へ進まず、設計判断へ戻る。

版・依存・通信の前提が決まらない段階で、製品driverやDB brokerを完成済みとして扱わない。

### 3.2 P1 動的な基準経路

最低限、次の操作を両DBで通す。

- PHPテーマの単一記事、一覧、検索、404、静的資産、redirect。
- pluginのfilter、shortcode、動的描画、REST、wp_head・wp_footer等への出力。
- ログイン、ログアウト、権限不足、CSRF拒否、記事編集と保存、非公開化。
- Cookie・header・locale・hook・global・DB接続の要求間分離。
- 同一要求内でテーマと複数pluginがフック・global・PHP objectを共有したときのWP互換性。
- DB rollback、要求timeout、PHP異常終了、Rust実行ホストまたはworker停止、終了処理。

動的応答の送信は採用済みA案として、echo等の出力が完成後に正しいstatus・header・bodyで返ること、生成途中では外部へ成功応答が出ないことを実HTTPで確認する。途中まで出力した後のtrap、出力上限・期限超過、flush呼出しを含める。即時の途中出力やSSEを必須とする機能を、初回対応済みと扱わない。

キャッシュを迂回する応答にも完成後送信の契約が適用されること、失敗前に確定したDB変更を誤って未実行と表示しないことを確認する。静的ファイルの配信・Rangeは別に回帰確認する。

PHP実行の隔離A案として、受入済みコードの共有は同じ要求内に限られ、別要求・別利用者へCookie・actor・hook・global等が漏れないことを確認する。一つの拡張によるtrap・timeoutで要求を失敗させる場合の全体回収、本体専有領域・別サイト・別役割への到達拒否を試す。個別プラグインだけを停止して要求を継続することは受入条件に含めない。

公開処理のDB書込みは採用済みA案として、匿名GETに伴う通常のWP・plugin更新が標準wpdb APIとRust管理DB経路から成功することを確認する。同時に、権限不足の編集・設定変更等がWP側で拒否され、DB直接接続や本体制御状態へのアクセスが許可されないことを確認する。公開書込みの許可を独自テーブル・DDLの一括許可として扱わない。

採用したDB互換方針A案に従い、標準wpdb APIの操作とSQL入力を比較する。SQL結果だけでなくwpdbの公開状態、sessionの変化、実装変更量、往復回数、latency、RSS、配布依存を測る。mysqli handle・driver固有resultの直接操作は、成功することではなく、利用するpluginが拒否されることを確認する。

接続候補1を先に実証する提案とし、必要な場合だけ接続候補2を比較する。標準APIの互換契約を満たせなければ、接続口を再設計する。採用した互換対象を黙って縮小したり、未解決のままキャッシュを有効化して差分を隠したりしない。

### 3.3 P2 DBとオブジェクトキャッシュ

DBはNULL・binary・数値・collation・結果順・挿入ID・更新件数・エラー・複数結果・session設定を比較する。同じsessionでのread-your-writes、transaction snapshot、savepoint、rollback、接続再利用の清掃を含める。

cacheはfalseとmiss、参照引数found、group、non-persistent、期限、objectの扱い、複数API、原子add・incr等を比較する。複数workerから同時に同じキーを操作し、実装内部のlockを呼んだだけの試験で代用しない。

期限を指定するplugin、transient、codecが難しいPHP値を含める。対応できない契約は明示し、支持していない機能をsupportsで申告しない。

### 3.4 P3 追跡と容量

snapshot中の更新、COMMIT前後、外部接続の更新、rollback、DDL、切断、rotation、必要ログの消失、DB再起動、別source、checkpointの破損・古さを試す。

変更を認識した後に旧値が新番号へ保存されないこと、複数HTTP processとworkerの停止・復帰、進行中の読取りと書込み、同時更新後の反映を確認する。監視socketの接続成功だけでHealthyへ移さない。

資源はcgroup上限縮小、親制限、不明な観測範囲、PHPのWasmメモリ・Rust実行ホストの増加、cache以外のRSS増加、再構築中、新旧本体二重起動を試す。手動容量入力なしで停止・縮小・復帰の理由が表示されることを確認する。

### 3.5 P4 応答と拡張受入れ

匿名とログイン、Cookie変種、認証header、preview、password保護、GET queryの重複・順序・encoding、locale、Vary、Set-Cookie、no-store、時刻・外部依存、GETの副作用を含める。

採用済みの応答キャッシュ方針A案として、保存可否を判断できない動的処理が毎回PHPで実行され、キャッシュ可能性だけを理由に拡張が拒否されないことを確認する。経路単位で影響を限定できない場合のサイト全体停止、理由表示、オブジェクトキャッシュ・DB最適化の個別判定も含める。

公開要求による書込みが追跡・失効へ接続され、その実行で書き込んだ応答が共有保存されないことを確認する。閲覧ごとの更新が必要な経路へ繰り返し要求し、キャッシュヒットによって必要な更新が省略されないことも確認する。

全パージ前の生成結果、旧ETagの304、Range、HEAD、コード変更、theme・plugin更新、uploads変更、複数processへの通知欠落を検証する。実際にHTTPへ渡った応答を観測し、cache内部の状態だけで合格にしない。

拒否試験には、キャッシュ差替え、db.php設置、独自DB接続、mysqli handle・driver固有resultの直接操作、専有設定変更、MU-plugin、theme経由、更新時だけ増える禁止機能、直接配置、復元による再導入を含める。理由表示、既存版の保持、実行環境側の拒否も確認する。

衝突の具体的な疑いが解消しない場合は、有効化保留とRP開発者への報告案内、診断資料の生成、秘密情報を含めない出力を確認する。未検証という理由だけの一律保留、応答キャッシュ可能性だけによる保留、報告しただけの解除が起きないことも確認する。policy・profile・本体・拡張の修正後は、対象hashを照合して再判定する。

報告窓口A案として、GitHub Issues向けの本文・診断生成、利用者の内容確認・コピー・書出し・受付ページ案内を確認する。自動送信せず、秘密情報をURLへ埋め込まず、未提出・到達不能を報告済みと表示しない。GitHub tokenを製品へ登録せずに提出の案内ができることと、Issueを記録しても保留が解除されないことを確認する。

複合プラグインは採用済みA案として、衝突しない機能と衝突機能を併せ持つ場合に全体を拒否することを確認する。衝突機能を設定offにした場合や無効化profileがある場合も、初回は許可しない。誤検出の修正や衝突を除去した新版の再検査と、設定offだけの例外受入れを区別する。

### 3.6 P5 内部索引

対応するquery shapeとsession条件を固定し、正本DBと結果・型・順序・可視時点を比較する。NULL、重複meta、LIKE、collation、ページ送り、filter、独自表、schema変更を境界に含める。

未対応条件ではDBへ戻り、壊れた索引・構築途中・追跡遅延で不完全な結果を返さない。効果が確認できなければ、その索引を標準経路へ昇格させない。

### 3.7 P6とP7 製品操作と継続運用

元WPの診断、拒否pluginの説明と代替、転送・file取込み、途中再開、最終同期、画面・HTTP比較、切替、切戻しを一つの操作シナリオにする。

OIDCは既決の3モード、全role、初期off、一度限り許可の競合・中断・再開・失効・復元を検証する。認証とPHP実行が可能になったことを理由に、連携専用sessionへ通常権限を付けない。

三環境で新規導入、再起動、code更新、binlog権限、DB切断、backup、別環境復元、秘密更新、新旧本体切替を行う。Composeの静的確認やLinux cross compileを、native実行・正式対応の代わりにしない。

採用済みの同梱基盤更新A案として、Rust本体・WP・php-wasm・実行ホスト・接続コードが検証済みの同じリリースへ切り替わり、個別部品の独立更新で固定組合せを迂回できないことを確認する。WP標準のコア更新入口、直接配置、途中失敗も試験対象にする。schema変更なしの差戻しと、schema変更ありのDB復旧を区別する。

## 4 初回リリースの判定

初回リリースは、採用した機能一覧・拡張policy・対応版・三環境・両DBと、次の操作を満たした時点で判定する。

| 操作群 | 判定するもの |
| --- | --- |
| 通常利用 | ログイン、編集、保存、公開、非公開化、削除、再起動後の継続 |
| WP標準機能 | 検索、一覧、REST、media、feed、comment等、固定基準の採用項目 |
| 拡張 | 受入済みtheme・pluginの比較、衝突するものの導入・更新拒否 |
| 高速化 | ミスとhit、外部更新、全失効、追跡不能、圧迫時も誤結果・誤共有を起こさない |
| 移行 | 両取込み方式、再開、最終同期、差分確認、切替判断 |
| 運用 | backupと別環境復元、更新失敗、秘密更新、状態と理由の表示 |

代表theme・pluginは検証材料であり、それ以外を自動的に不対応または対応済みと判定しない。個別に受入policyと互換profileを適用する。

## 5 既存実装の扱い

2026-10-30の[実装照合記録](../../implementation-design-reconciliation-2026-10-30.ja.md)を現在地の参照元とする。最新Cookie照合取り込み後の全体再検証は未完了であり、旧checkpointの成功を新構成の成功へ流用しない。

| 現在の実装 | 再利用する候補 | そのまま流用しない部分 |
| --- | --- | --- |
| recastpress-server | HTTP、Host検証、条件付き要求、静的配信、CLI | 起動時にbundleを封印することを全動的配信の必須条件にする構造 |
| recastpress-core | cache世代、資源予約、失効、共有body等の部品 | process内のrevisionだけで分散失効・公開撤回まで達成したとする接続 |
| recastpress-db | raw値、限定lookup、sessionやfixtureの知見、変更追跡部品 | raw reader・CASをwpdb互換driverやWP保存全体と見なすこと |
| recastpress-wp | 固定WPとの比較手法、必要なpure処理、互換資料 | 全APIをRustへ移すことを必須とする開発順、独立した認証正本 |
| Wasm独立実験 | 回収、資源、所有、要求分離の検証の考え方 | RustテーマComponentのABIをphp-wasmのABIとして使うこと |
| bundle・package・receipt | 不変成果物、importの検査、静的出力、検証用配布 | checksumを署名・由来・公開承認と同一視すること |
| DB・HTTP・互換fixture | 障害シナリオ、所有processの回収、比較と証跡固定 | 有限のWindows試験を常駐Linux製品・全plugin互換とすること |

既存コードの削除は本案作成では行わない。再利用・保留・置換の単位をP0で決め、再利用する範囲に必要な検証を行う。新構成で使わない互換APIを増やし続けることは、実装順から外す。

## 6 比較環境と証跡

比較基準は、固定したWPソース・通常PHP・対応DB・同じtheme・plugin・同じ初期データを使う。最適化なし、object cacheのみ、追跡あり、応答cacheあり、索引ありを段階別に比べる。

出力差分を比較するときは、nonce・時刻・乱数・ID等を識別し、許可した差分だけを正規化する。正規化によって認証や更新の差分を消さない。SQL、hook順、DB状態、Cookie、header、body、画面の関係を必要な操作ごとに記録する。

証跡は、source hash、lock、依存・版、環境、設定、入力、出力、計測時刻、対象範囲に対応させる。古い実測を現在sourceの成功へ付け替えず、再利用した過去結果と今回再実行した結果を区別する。

## 7 性能と運用の数値目標

具体的な合格値は未決である。次の測定項目から、P0〜P1で基準値を取得し、P3〜P4の有効化前に許容値を合意する。

| 分野 | 指標 |
| --- | --- |
| HTTP | cold・warm・全失効後のp50・p95・p99、同時数、転送量、error率 |
| DB | 物理query数、待機、実行時間、往復、接続数、書込み負荷 |
| キャッシュ | hit率だけでなくbypass理由、誤共有0件、旧値の最大利用時間 |
| 追跡 | 初期構築時間、取得遅延、適用遅延、停止判定時間、再構築時間 |
| メモリ | Rust本体・実行ホストのRSS、PHPのWasmメモリ、cgroup全体、論理予算、peak、圧迫時の継続性 |
| 運用 | 導入・移行・更新・復元の所要時間と利用者の操作数 |
| 費用 | 三環境の通常構成の月額と、DB・保存・転送を含む前提 |

性能改善率を先に約束しない。DB接続仲介やWasmの追加費用が効果を上回る場合は、移す範囲・往復・共有方法を見直す。対象サイトに対する価値が出なければ、実装量の増加で埋め合わせない。

## 8 未決事項

DB互換範囲は2026-11-01にA案で決定済みとし、未決から外す。標準wpdb APIを互換対象とし、mysqli接続handle・driver内部へ直接依存するpluginは拒否する。具体的な接続方式と標準APIを実現する方法は、引き続き実装側の実証対象とする。

応答キャッシュの保存可否が不明な場合の扱いも、同日にA案で決定済みとする。当該処理は毎回PHPで実行し、影響を限定できなければサイト全体の応答キャッシュを停止する。キャッシュ可能性だけで拡張を拒否しない。具体的な適格性の確認方法と範囲の切り分けは、引き続き設計・実証する。

具体的な基盤衝突の疑いが解消しない拡張の扱いは、同日にA案で決定済みとする。有効化を保留し、RP開発者への報告を求める。検査・再判定の実装詳細を残件とする。

公開処理のDB書込みも同日にA案で決定済みとする。標準wpdb APIとRust管理経路で通常のWP処理に必要な書込みを許可し、操作の認証・認可はWPとプラグインが担う。権限の物理配置・実行profileの詳細は実装側で具体化し、独自テーブル・DDLは別判断として残す。

同梱基盤の更新は同日にA案で決定済みとする。Rust本体・同梱WP・php-wasm・実行ホスト・接続コードの取込み・組合せ検証・配布をRP側が担う。部品ごとの独立更新は提供しない。自動適用する版の範囲、時刻、schema変更ありの適用・復旧、修正配布期限は残件とする。

php-wasm実行ホストは同日にB案で決定済みとし、Node.jsを製品の実行依存にせずRustから直接実行する。PHPビルド・Wasmエンジン・ABI・ホスト機能の選定と成立実証を残件とし、P0の通過条件へ置く。

動的応答の送信は同日にA案で決定済みとし、初回は有限サイズで完成後に送信する。通常のPHP出力は維持し、即時の途中出力を必須とする機能は初回非対応とする。物理的な保持方法、上限値、期限、失敗応答を残件とする。

PHP実行の隔離も同日にA案で決定済みとする。受入済みテーマ・プラグインは同じ要求のPHP環境を共有し、隔離単位はサイト・役割・ワーカーとする。プラグイン間の完全隔離は要求しない。物理配置、要求の清掃、異常回収、本体専有領域の保護を実証する。

複合プラグインも同日にA案で決定済みとする。一部に衝突機能を含む場合は初回は全体を拒否し、設定off・無効化構成の例外受入れを行わない。判定・理由表示・再検査の実装を残件とし、受入単位の選択は未決から外す。

報告窓口も同日にA案で決定済みとし、GitHub Issues向けの公開可能な診断と報告文を生成し、利用者が確認して投稿する。自動送信や専用の非公開受付サービスは初期機能へ追加しない。

これで今回の新構成に伴う方針確認10件は完了とする。残件を、採用した方針内で実装側が調査・実証する項目と、旧案から引き継ぐ製品・運用条件へ分ける。以下の行数を追加の質問回数と同一視しない。

### 8.2 旧案から引き継ぐ製品と運用の条件

次の条件は今回新たに増えた方針確認10件とは別に扱う。対応可否を再質問する代わりに、代表データや実測から具体案をまとめる。利用者の操作・互換性・停止・費用等を変える製品条件は、その段階で判断する。

| 論点 | 残る条件 | 確定が必要な時点 |
| --- | --- | --- |
| 独自tableとDDL | 管理された登録・更新経路、通常要求でのDDL、許可能力を定める | P1の拡張受入れ前 |

未決事項を詳細設計の空実装で成功扱いしない。一方、標準WPで決まる機能の採否を再質問する代わりに、固定ソース・比較profile・接続条件から実装する。

## 9 次の具体的な作業

最初の実装成果物は、Node.jsなしでRustからPHPのWasmを実行し、入出力・ファイル・ホスト呼出し・清掃・回収を確認するP0の実証とする。その成立後、Rust HTTPからphp-wasmを経由して、既存PHPテーマ・plugin・WP処理と両DBを使う、キャッシュなしの比較用サイトをP1で作る。

その前に、DB接続候補と拒否policyの最小契約を確定する。試作で確認した往復・型・資源・要求分離を使って、DBとキャッシュの設計を絞り込む。旧方式の全API移植やRustテーマSDK開発を、新しい基準経路より先に進める順番にはしない。
