# RecastPress 新構成の概要設計案

作成日：2026-11-01（日本時間）  
版：0.5  
対応する実装の開始版：0.5.0  
状態：議論用の新規設計案

RecastPressを、キャッシュとDBハンドリングを独自実装するRust製のWordPress専用Webサーバーとして設計する。WPの要求処理、テーマ、プラグイン等はサーバー内部のphp-wasmで実行し、既存PHPコードを活用する。WP製品全体のRust再実装と、利用者によるテーマのRust移植を前提にしない。

この案は既存の[詳細設計 v0.45](../../design.ja.md)とは独立している。既存の要求R01〜R61、試験T01〜T44、判断記録を上書きしない。下記の「議論で確認した方向」と「具体化の提案」を区別し、文書の版指定を詳細の一括採用や個別機能の実装完了とは扱わない。

2026-11-01のユーザー指定により、新設計の文書はv0.5、対応する実装は0.5.0を開始版とする。実装workspaceの版を0.1.0から0.5.0へ切り替え、以後の新構成の開発をこの系列で管理する。版の切替時点でphp-wasmや新DB経路が実装済みになるわけではなく、未決事項は引き続き個別に判断する。

## 2 製品の価値

既存のWPサイトを維持しながら、キャッシュとDB処理を予測可能にし、設定・調査・障害対応の負担を減らすことを主な価値とする。RustやWasmの使用自体を、速度・安全性・低費用の達成と同一視しない。

利用者には、既存テーマをRustへ移植せずに使えること、キャッシュとDBの状態・停止理由を一か所で確認できること、メモリの手動調整を減らせることを提供する。性能は通常のWP構成と比較し、キャッシュヒット時だけでなく、ミス・更新・障害・復帰時まで測る。

対象像は従来の企業・商品紹介・カタログ・ブランディング・通常のLP・個人サイトを引き継ぐ。単一サイト月間20万PVまでという想定は、瞬間負荷の保証に置き換えない。CDNは必須にせず、追加する場合の失効と責任は別に定める。

## 3 議論で確認した方向

| 方向 | 内容 |
| --- | --- |
| Rustの位置付け | WP専用Webサーバーを入口とし、製品の基盤をRustで実装する |
| PHPの位置付け | WPの周辺処理には要求対応も含め、php-wasmで既存PHPを実行する |
| php-wasm実行ホスト B案 | Node.jsを製品の実行依存にせず、RustからPHPのWasmを直接実行する。必要なPHPビルド・ABI・ホスト機能の成立を先に実証する |
| 動的応答の送信 A案 | 初回はPHP応答を有限サイズで完成させてから送信する。即時の途中出力が必須の機能は初回非対応とし、通常のPHP出力は維持する |
| PHP実行の隔離 A案 | 受入済みテーマ・プラグインは同じ要求のPHP環境を共有する。隔離はサイト・役割・ワーカー単位とし、プラグイン間の完全隔離は保証しない |
| テーマ | テーマとfunctions.phpのRust移植を廃止する方向で設計する |
| 独自機能 | キャッシュとDBハンドリングを製品の中心に置き、WPとの互換性を維持する |
| DB互換方針 A案 | 標準の `$wpdb` APIを互換対象とし、mysqli接続handle・driver内部へ直接依存するプラグインは拒否する |
| 公開処理のDB書込み A案 | 公開要求でも通常のWP処理に必要な書込みを、標準 `$wpdb` APIからRust管理のDB経路を通して許可する |
| 応答キャッシュの判定不能時 A案 | 保存可能性を確認できない処理はキャッシュを迂回して毎回PHPで実行する。キャッシュできないことだけを理由に拡張を拒否しない |
| プラグイン | 本体が専有する機能を置換・迂回・無効化するプラグインは導入を拒否する |
| 複合プラグイン A案 | 衝突機能を一部に含む場合、初回はプラグイン全体を拒否する。設定offや無効化構成の例外受入れは行わない |
| 衝突判定が不明な場合 A案 | 具体的な衝突の疑いが解消するまで有効化を保留し、RP開発者への報告を求める。未検証という理由だけでは一律保留にしない |
| 報告窓口 A案 | 通常の互換性報告はGitHub Issuesで受け付ける。秘密情報を除いた診断と報告文を生成し、利用者が確認して投稿する |
| 同梱基盤の更新 A案 | Rust本体、同梱WP、php-wasm、実行ホスト、接続コードを、RPの検証済みリリースとして一体管理する |
| 今回の成果物 | 既存仕様書を変更せず、新しい設計案を作る |

具体的なDB接続方式、拒否判定方式、メモリ算式、反映期限、初回の検証対象は後述の提案・未決事項である。

DB互換方針のA案は2026-11-01にユーザーが採用した。標準APIの戻り値・公開状態・SQLの意味の互換性は維持するが、プラグイン向けの生のmysqli handleやdriver固有resultの互換実装は要求しない。Rustへの接続方式は、この採用範囲を満たす実証で選ぶ。

公開処理のDB書込みも同日にA案を採用した。公開GETを含め、WPとプラグインによる操作の認証・認可・入力検査を維持したうえで、通常処理に必要な書込みを許可する。書込みは本体経路で追跡し、その実行で書込みが発生した応答を共有保存しない。DB直接接続・本体制御状態の改変・DB管理権限は許可せず、独自テーブル・DDLの可否は別途判断する。

応答キャッシュの判定不能時のA案も2026-11-01にユーザーが採用した。保存可能と確認できた応答だけを共有し、不明な処理は通常のPHP実行へ回す。影響範囲を限定できない場合はサイト全体の応答キャッシュを停止する。オブジェクトキャッシュとDB最適化は、それぞれの条件で利用を判定する。本体基盤との衝突や禁止能力の判定とは分ける。

同日に、具体的な基盤衝突の疑いが解消しない拡張は有効化を保留し、RP開発者への報告を求めるA案を採用した。製品は保留理由と報告用の診断資料を提示する。報告しただけでは有効化せず、調査結果を反映した再判定で解除する。

同梱基盤の更新も同日にA案を採用した。RP開発者が、同梱WP・php-wasm・実行ホスト・接続コードの修正を取り込み、Rust本体と合わせて検証・配布する。利用者が同梱部品だけを独立更新する構成にはしない。自動適用する版の範囲、時刻、DBスキーマ変更時の処理と復旧は別途定める。

php-wasmの実行ホストは同日にB案を採用した。Node.jsの同梱案を置き換え、Rustによる直接実行を製品方針とする。既存のPlayground向けWasmがそのまま動くことは前提にせず、PHPのWasmビルド・ホスト機能・境界契約をP0で調査・実証する。成立しなければ設計判断へ戻り、Node.jsやネイティブPHPへ自動的に方式を変更しない。

動的応答の送信は同日にA案を採用した。初回はPHP処理の完成後に応答を確定し、外部へ送信する。通常のecho等は利用できるが、即時の途中出力・SSE等を必須とする機能は初回非対応とする。静的ファイルの大容量配信・Rangeは別に扱う。出力上限・期限を超えても途中送信へ自動変更せず、失敗応答と終了処理へ進む。

PHP実行の隔離も同日にA案を採用した。受入済みコードはWPのフック・global・objectを同じ要求内で共有し、一つの信頼範囲として扱う。拡張ごとに別Wasm環境へ分割して標準フックを仲介する構成を必須にしない。要求間の利用者状態等の分離、本体専有領域の保護、衝突時の拒否・保留・報告は維持する。

複合プラグインの扱いも同日にA案を採用した。本体との衝突機能を含むことが判明した場合は、初回はプラグイン全体の導入・更新・有効化を拒否する。衝突機能を設定でoffにしても許可せず、そのプラグインの衝突しない機能も利用対象から外れることを説明する。

報告窓口も同日にA案を採用した。通常の互換性報告はRP公式リポジトリのGitHub Issuesを使い、製品が秘密情報を除いた診断資料と報告文を生成する。利用者が内容を確認し、自分で投稿する。自動送信、GitHub tokenの製品登録、専用の非公開受付サービスは初期機能へ追加しない。

今回、新設計で増えた方針として一件ずつ確認した10件は決定済みとする。以後は既決の範囲で技術調査・実証を進め、互換範囲や利用者の負担を変更する必要が出た場合だけ再確認する。旧案から引き継ぐDDL・反映期限・認証手続き・更新復旧・性能等の運用条件は、別の残件として管理する。

## 4 Rustへ移すコアの定義

Rustへ移す範囲は、データへのアクセス、キャッシュの保持・失効、資源配分、実行管理、HTTP配信を中心とする。WPのURL解釈、検索条件構築、保存フック、認証判断、テーマ選択等は、初期段階ではPHP実装を再利用する。

WPで中心的な機能であることだけを移植理由にしない。境界を固定でき、意味の同等性と効果を確認できる処理から移す。Rust版WP API全体の完成を、初回リリースの前提から外す。

### 5.1 プラグイン機能を吸収する範囲

| 分野 | 本案での扱い |
| --- | --- |
| ページキャッシュとオブジェクトキャッシュ | 本体が担当する。競合する実装の持込みを拒否する |
| DBアクセス制御と性能診断 | 本体が担当する。SQL分析の完全な代替ツールまでは含めない |
| PHP実行制御と診断 | 本体が担当する |
| OIDC SSO | 元案の標準提供目標を継承。認証セッションとの接続は設計する |
| バックアップと復旧 | 製品として必要な整合バックアップ・復旧手順を設計する。汎用バックアップ製品全体の吸収は別判断 |
| SEO、画像変換、CSSやJSの最適化 | 本体への吸収を追加しない。対応するPHP拡張の受入れは別に判定する |
| フォーム、EC、会員機能 | 本体へ吸収しない。プラグインとしての互換性や受入れは機能ごとに検証する |

機能分野の名称だけで拒否しない。本体との衝突が実際にあるかを判定する。複合プラグインの一部に衝突機能がある場合は、採用済みA案に従い初回は全体を拒否する。設定上offである場合も、確認済みの無効化構成である場合も、初回の例外受入れにはしない。衝突の有無を確定できない場合は、保留と報告の方針を適用する。

## 6 元案から捨てる仕様と置き換える仕様

| 元の仕様や実装前提 | 本案での置換 | 元の要求 |
| --- | --- | --- |
| WP製品全体のRust移植、RustだけをCMSコアとする | 基盤と選択したコア処理をRustへ移し、必要なPHP版WPコアを残す | R02、R04 |
| ネイティブPHP別プロセスと独自WP API全体の再現 | php-wasmを実行する内部サービスと限定的な接続層 | R05 |
| 公開要求からのPHP全面禁止 | Rust管理下の要求ごとのPHP実行を許可 | R06、R07 |
| 利用者AIによるRust移植、専用SDK、RustテーマのWasmビルド | PHPテーマの受入れ、互換診断、比較試験 | R10、R14、R17、R18、R46 |
| 検索・フィード・コメント・通知等を全面的にRust実装 | 提供機能を維持し、PHPを再利用する。個別の高速化は後段 | R21、R24〜R26、R29、R30、R32 |
| 公開処理は編集DBへ到達できず、事前検証した公開世代だけを参照 | Rust HTTP入口から資格情報を分離し、内部WP実行系が制御されたDB経路を利用 | R33、R61の実現方法 |
| 利用者にテーマ移植を担ってもらう | 互換診断、設定、比較確認、切替判断を利用者が行う | R53、R54 |
| 任意の基盤差替えを許す拡張環境 | 本体専有領域を予約し、衝突する拡張は拒否 | プラグイン受入条件の具体化 |

応答を「公開世代」へ封印する方式を全動的要求の必須条件から外す。一方、拡張コード・設定・失効番号・内部索引の世代管理は維持する。既存bundleは静的な公開物や検証の用途で再利用を検討する。

## 8 互換性の定義

互換性は、対応版・構成・許可された拡張能力の範囲で、APIの戻り値、PHPの型、フック、状態変化、SQL結果、権限判定、HTTP応答が比較基準と一致することで判断する。本体専有基盤の差替えは、明示的な非対応とする。

テーマ・プラグインが同じPHP要求内で関数・クラス・オブジェクト・フックを共有できることを重視する。すべての第三者コード、任意の拡張ライブラリ、任意のOS操作を無条件に互換とはしない。拒否対象と単なる未検証を区別して表示する。

本体が機能を吸収した場合でも、既存プラグインの設定・保存データを無断変換しない。移行診断で代替範囲と手順を示し、元データを保持する。

## 9 議論する順序

1. 本体が専有するDB・キャッシュ・実行領域と、許可するWP拡張の契約を確定する。
2. Node.jsなしのRust直接実行に必要なPHPビルド・ABI・ホスト機能を調査し、成立を実証する。
3. php-wasmとRustのDB接続方式を実証し、採用した標準wpdb API互換を実現する。
4. キャッシュの適格性確認方法、外部更新の反映遅延、非公開化の期限を決める。
5. 採用した拡張の導入・更新拒否と、保留時の報告・再判定を具体化する。
6. 最小サイトの受入操作と性能・資源・復旧の数値目標を決める。
7. SSO、移行、三環境、本体更新を順に製品経路へ接続する。

詳細な選択肢と、各判断が必要になる実装段階は[実装順と受入条件](implementation-and-validation.ja.md)に示す。
