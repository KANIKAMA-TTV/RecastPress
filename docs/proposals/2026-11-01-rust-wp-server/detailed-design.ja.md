## 1 不変条件

| 項目 | 条件 |
| --- | --- |
| 正本 | WP互換DBと管理されたファイルを正本とし、キャッシュ・内部索引を唯一の原本にしない |
| PHP実行 | テーマ・プラグイン・WP処理を同じ要求コンテキストで実行する。要求間のPHP変数・Cookie・actorを混在させない |
| DB | 結果、型、順序、照合、エラー、トランザクション可視性を、対応範囲で維持する |
| 書込み | 成否不明を成功・失敗へ推測せず、変更SQLを無条件に再実行しない |
| キャッシュ | 適格性、コード版、失効番号、追跡状態が成立する値だけを共有する |
| 資源 | 各処理に有限の実行・保持・待機境界を持たせ、手動キャッシュ容量設定を要求しない |
| プラグイン | 本体専有領域の置換・迂回・無効化を許さない。通常のWP拡張は区別する |
| 権限 | 採用済みA案に従い、同一PHP要求内の受入済みテーマ・プラグインを一つの信頼範囲とする。サイト・役割・ワーカーの境界と要求間の状態分離、ホスト側制限を維持する |
| 復旧 | コードの差戻し、DBの復元、キャッシュの消去を異なる操作として扱う |

## 2 要求と内部通信の契約

### 2.1 要求コンテキスト

Rust入口が次の情報を生成する。内部制御情報は外部HTTPヘッダーから直接引き継がない。

| 項目 | 内容 |
| --- | --- |
| request_id | 要求とDB・PHP・診断を関連付ける識別子 |
| site_idとrole | 対象サイト、許可された実行プールと能力 |
| deadline | 内部待機を含む全体期限。各呼出しに残り時間を渡す |
| code_revisionとsettings_revision | WP・テーマ・プラグイン・接続コードと設定の固定版 |
| cache_epoch | 要求開始時の共有失効番号。最終利用・保存時にも照合する |
| methodとrequest_target | 元のmethod、パス、クエリーを保持した要求先 |
| headersとbody | 複数値を保てるヘッダー列、有限サイズのbodyまたは入力ストリーム |
| session_handle | 当該要求のDBセッション等を関連付ける偽造困難な内部handle |

Cookie、Authorization、ログインコード、パスワード、記事本文、SQLのリテラルを通常の診断ログへ書かない。request_idは認可tokenとして使わない。

### 2.2 接続とフレーム

Rust実行ホストとDB・cacheサービスを分離する場合、通信の初期候補は同一ホストのUnix domain socket、配備上必要なら認証付き内部TCPとする。loopbackや内部ネットワーク上であることだけで認証を省略しない。双方が対向の役割と対象サイトを確認する。同一プロセスへまとめる場合も、ホスト関数の能力境界と期限・取消の契約を維持する。

RPCは契約版、操作種別、相関ID、payload長、期限を持つ。JSONだけに統一して非UTF8のPHP文字列やDB値を損失変換しない。制御metadataとバイナリpayloadを分ける案とする。最大フレーム・入出力・同時要求数は実装側の有限値とし、P0〜P1で決める。

同じストリームで逆方向のDB・キャッシュ呼出しを扱う場合、要求実行中にRust側がPHP完了だけを待って双方が停止しないよう、応答と内部呼出しを独立に処理する。再入、取消、途中切断、期限の伝播を受入試験に含める。

### 2.3 PHP応答

応答はstatus、重複を保持するheaders、複数Set-Cookie、body、実行結果、キャッシュ依存の申告を返す。PHPの申告は保存を許す十分条件にせず、Rust側の禁止条件で上書きできる。接続固有ヘッダー等の扱いを決め、外部へ内部診断を出さない。

予約された本体APIと通常WPルートの優先順位を明示し、ルート競合を導入時に拒否する。任意ファイルパスを外部要求からPHPの実行ファイルへ直接変換しない。WP標準の入口と受入済みのプラグイン入口を配布manifestへ登録する。

### 2.4 動的応答の完成と送信

**決定 2026-11-01**：動的応答の送信はA案を採用し、初回はPHP処理が完成した応答を有限サイズで保持・検査してから、外部へ送信する。通常のecho等は利用できる。PHP側のheader確定・出力buffer等の内部挙動と、Rustが外部へ送信するタイミングを分けて比較する。

Rustホストは出力を内部で順次受け取ってよいが、処理完了前に成功status・header・bodyを閲覧者へ送らない。内部RPCのフレーム分割やDB・cacheのコールバックを禁止する意味ではない。

| 状態 | 動作 |
| --- | --- |
| PHP処理が正常に完成 | 検査後、PHPが指定したstatus・header・bodyを返す。正常に生成した4xx・5xxもそのstatusを維持 |
| 出力上限・期限超過、trap、ホスト異常 | 途中出力を成功応答として送らず、固定した失敗分類に従う応答を返す。PHP・DB・資源の終了処理へ進む |
| 即時の途中出力・SSEが必須 | 初回の未対応能力として診断し、対応済みと表示しない |

バッファと生成中の値を共通資源予算へ計上し、上限を超えても外部ストリーミングへ自動変更しない。物理的な保持方法、上限値、期限、HTTP失敗statusは実証と運用条件から決める。キャッシュ不可の応答にも同じ送信契約を適用する。

PHPのflush等を呼べることだけを、即時送信の互換性として扱わない。そのタイミングに依存する拡張は未対応として判定する。静的ファイルの大容量配信・Rangeは別契約で維持する。

応答を送らなかったことは、既にCOMMITしたDB変更や外部送信を取り消した証明ではない。取消・結果不明・再試行は第3章と第7章の契約に従う。

## 3 DBハンドリング

### 3.1 役割

Rust DBサービスが実際のDB接続、接続先資格情報、セッション、計測、制御状態を所有する。PHP側にはWP互換の入口を提供する。DBサービスは、任意SQLを解釈する独自DBエンジンにはしない。

クエリーの生成、WPのfilter、保存フック、投稿・ユーザー・権限の意味はPHP側に残す。RustがSQLを実行したことだけを、操作の認可済み証明にしない。

### 3.2 採用した互換方針と接続方式

**決定 2026-11-01**：DB互換方針はA案を採用する。標準の `$wpdb` API、その戻り値・公開状態・SQLの意味を互換対象とする。mysqli接続handle、driver固有result、DBドライバー内部を直接操作するプラグインは拒否する。

例えば `$wpdb->dbh` をmysqli関数へ渡すことや、`$wpdb->result` をnative resultとして操作することは互換対象に含めない。`last_result`、`last_error`、`insert_id` 等の標準API利用から観測される状態は維持する。通常の `$wpdb` 経由SQLを拒否する決定ではなく、独自table・DDLの許可を一括決定するものでもない。

以下は実装手段の候補であり、会話で採用した互換方針A案とは別の選択軸とする。混同を避け、接続候補は1・2で表す。

| 候補 | 方式 | 利点 | 確認が必要な点 |
| --- | --- | --- | --- |
| 1 | 本体所有のdb.php・wpdb接続層からRust RPCへ渡す | request_id・SQL結果・失敗を明示的に対応付けやすい | wpdb内部のdriver依存、標準APIの型・文字コード・escape・再接続・公開状態を維持する実装 |
| 2 | PHPのDBドライバーを維持し、RustがMySQLプロトコル接続を仲介する | 本体内部でdriver由来のPHP型・resultを維持しやすい | php-wasmのdriver、ホストのTCP仲介、TLS、認証、prepared statement、要求との接続対応、プロトコル処理量 |

採用した互換範囲と実装規模を踏まえ、P1では接続候補1を先に小さく実証する提案へ変更する。候補2との全面的な比較実装を必須にせず、候補1で標準API互換性や実装規模に問題が判明した場合に候補2を比較する。どちらを使っても、拒否対象のdriver直接操作をプラグインへ提供する理由にはしない。

候補1を「薄い接続口」だけで完成すると見積もらない。標準APIを実現するために必要なwpdb内部のdriver依存を洗い出す。受入条件を満たせなければ、後続最適化へ進まず境界を再設計する。候補2を比較する場合も、素通しTCPや任意SQLの正規表現判定だけで完全なCOMMIT・更新結果の検出を保証しない。

採用した実行ホストB案では、Node向けのDB接続機能をそのまま利用できるとはしない。RustでホストするPHPビルドとDB接続口の成立をP0〜P1で実証する。接続候補1はPHPからRustのDB操作を呼ぶ境界、候補2は必要なdriverとホスト側I/Oの成立が前提となる。[既存のPHP.wasm実行基盤](https://developer.wordpress.org/playground/developers/architecture/wasm-php-overview/)、[WP DB初期化](https://developer.wordpress.org/reference/functions/require_wp_db/)

### 3.3 DBセッション

セッションはsite、実行ロール、request、接続世代と対応させる。開始後は同じDB接続へ固定し、SQLごとの無条件な接続振替を行わない。

次の状態を保持する。

- 文字コード、collation、sql_mode、time_zone等の接続設定。
- autocommit、トランザクション状態、分離レベル、savepoint。
- 一時表、ユーザー変数、接続依存のIDや関数、取得したlock。
- prepared statement、結果の読取り状態、警告、エラー、更新件数、挿入ID。

WP標準が要求する接続設定と、拡張が変更できる設定を契約化する。読取りSQLに見えても `SELECT ... FOR UPDATE`、一時表、ユーザー変数、stored function等の副作用や接続依存を持ち得るため、SQLの先頭語だけで最適化しない。

要求終了時に未完了transactionや未読結果を清掃する。完全なリセットを確認できない接続は破棄し、別要求へ貸し出さない。PHPインスタンス再利用とDB接続再利用は別々に可否を決める。

### 3.4 PHPから観測できる互換性

| 領域 | 比較するもの |
| --- | --- |
| 値 | NULL、空文字、数値文字列、符号、巨大整数、小数、binary、非UTF8、日時 |
| 結果 | 列metadata、重複した列名、行順序、複数結果、object・arrayへの変換 |
| 更新 | rows_affected、insert_id、0件更新、REPLACE、エラー後の公開状態 |
| wpdb | last_result、last_error、last_query、num_rows、num_queries、format・prepare・escape、結果取得mode |
| DB状態 | 同一要求のread-your-writes、transaction snapshot、rollback、savepoint、lock、接続設定 |
| 拡張 | 標準のwpdb filterと、標準API・本体接続経路を保つ拡張。mysqli handle・driver固有resultの直接操作は拒否対象として検証 |

PHP値の仕様をRustのStringやJSON numberへ一律変換しない。型やDB metadataの扱いは接続方式選定時に固定し、黙って精度を落とさない。[wpdb公式仕様](https://developer.wordpress.org/reference/classes/wpdb/)

### 3.5 SQLの許可範囲

通常の `$wpdb` による読取り・データ更新は、対応するWP処理の互換対象とする。本体の独自制御状態・他サイト・DB管理権限へのアクセスは禁止する。

**決定 2026-11-01**：公開処理のDB書込みはA案を採用する。公開GETを含む通常のWP処理に必要な書込みを、標準wpdb APIからRust管理DB経路へ渡して実行できるようにする。公開要求であることだけを理由に読取り専用へ制限しない。操作の認証・認可・入力検査はWPと受入済みプラグインが担い、匿名での任意の編集・設定変更を許可する意味ではない。

書込みの追跡、失効、結果不明の扱いは第5章に従う。その実行で書込みが発生した応答は共有保存しない。生のDB接続、本体制御状態の改変、DB管理権限を新たに開放せず、独自テーブル・DDLの許可もこの決定に含めない。

プラグイン独自テーブル、CREATE・ALTER等のDDL、外部DB、stored routine、FILE権限等は別能力とする。初期の既定案は、独自テーブルの登録とDDLを導入・更新の管理処理で検査すること。一般要求へ任意DDLを許すかは未決とし、禁止による非互換を隠さない。

許可したDDLはDB固有の暗黙COMMITを含む意味を維持する。製品が外側にtransactionを置けばすべてrollbackできるとはしない。DDL後はschemaを再確認し、影響する内部索引を停止・再構築する。

DBへの直接接続をプラグインへ自由に開放しない。Rust管理の接続経路を使うことと、WP経由の通常SQLを許すことを両立させる。OSユーザー、接続先の制限、ネットワーク経路、資格情報の配置で迂回を防ぎ、SQL文字列の検査だけに依存しない。

未知SQLの副作用や更新の完了を確定できなければ、影響する共有高速経路を停止したまま通常DBへ通す。判定できないSQLを読取り専用として扱って再利用しない。SQLを許すかという能力判定と、その結果を高速化できるかという同等性判定を分ける。

### 3.6 失敗と再試行

結果は、確定成功、DBが返した確定エラー、実行前の不成立、実行結果不明、接続清掃失敗へ分ける。COMMIT送信後の切断を確定失敗にしない。

副作用のあるSQLは無条件に再送しない。読取りでも接続・snapshot・lockの意味が変わる再送を自動化しない。上流wpdbの再接続・再実行と、Rust側の再試行が重ならないよう、両方の責任と比較基準を固定する。安全性のために上流と異なる結果分類を返す箇所は、明示的差分として承認する。

### 3.7 内部索引

初期は索引なしで正本DBへ処理を通す。次に、raw値・重複・参照を維持できるID lookup等から候補を選ぶ。任意SQLのメモリ実行、全テーブル常駐、正本schemaへの自動索引追加は初期範囲に含めない。

高速経路は対象のquery shape、schema、collation、session設定、可視時点、追跡位置を確認する。transaction中、独自設定、未対応filter、未知schema等で結果同等性を確認できなければDBへ戻る。SQL文字列が一致しただけで安全と判定しない。

WP_Queryのfilterやhookが観測するSQL・結果・計数を飛ばさない。実際にはDBへ問い合わせなかった場合の診断計数も、互換上の表示と物理実行計測を分ける。

## 4 キャッシュ

### 4.1 共通基盤

応答、オブジェクト、内部データ・索引は、共通の自動予算管理を使う。ただしキー、値の意味、期限、失効、機密性は別namespaceに分ける。オブジェクトキャッシュには認証・非公開情報が入り得るため、公開HTTPの共有応答キャッシュと同じアクセス権を与えない。

共通metadataの案はsite、namespace、code_revision、schema_version、cache_epoch、キーの元表現、作成時の追跡条件、値の型・codec、論理サイズ、必要なら期限とする。キーのhashは検索補助に使い、衝突があっても異なるキーを同じ値として返さない。

値・キー・管理情報・未完了の保存予約・退避中に残るownerを予算対象へ含める。実RSSと論理予算は別々に観測し、論理値が下がれば即座にOSへ返却されたとはしない。

### 4.2 WPオブジェクトキャッシュ

本体所有のobject-cache接続コードを使い、WPのAPIからRustへアクセスする案とする。次を比較して実装する。

- キーの正規化、group、global group、non-persistent group、siteの切替条件。
- 保存値falseとmissの区別、参照引数found、forceの意味。
- set、get、delete、add、replace、incr、decr、複数件API。
- flush、flush_group、flush_runtime、supportsによる機能申告。
- 明示された有効期限、期限なし指定、期限境界、再起動・退避による消失。
- PHP objectのclone、型、参照、要求内の変更と、共有保存時のcodec。

add・replace・incr・decr等の原子性が必要な操作は、Rustサービスの単一操作として確定させる。PHP側のget→setで代用しない。複数プロセスのローカルcopyが存在する場合、その整合を含める。

初期は要求内PHPキャッシュとRust共有層を組み合わせ、要求内だけの値を共有へ出さない。PHP objectをJSON化するだけで互換としない。serialize・unserializeでもmagic method等の観測が変わり得るため、codecと対応する値をP2で検証する。未対応の値を別型へ変換したり、必要な共有機能を要求内だけの保存へ黙って置き換えたりしない。

共有値の復元は、対象code_revision・codecと対応させる。コード更新後に古いクラス定義のobjectを復元しない。PHPの復元コードは信頼された共有サービスからの値のみを扱い、外部入力を直接復元させない。

期限指定はWPの契約に従う。応答キャッシュのTTLなし方針を、wp_cache_*やtransientの期限無視へ拡張しない。[WPオブジェクトキャッシュ](https://developer.wordpress.org/reference/classes/wp_object_cache/)、[wp_cache_get](https://developer.wordpress.org/reference/functions/wp_cache_get/)

### 4.3 応答キャッシュの適格性

**決定 2026-11-01**：保存可能性を判断できない場合はA案を採用し、当該処理を応答キャッシュから迂回させて毎回PHPで実行する。キャッシュできないことだけを理由に、通常の動的処理を提供するテーマ・プラグインの導入を拒否しない。

影響範囲を特定の要求・経路に限定できなければ、サイト全体の応答キャッシュを停止する。設定値の初期onと実利用を区別し、停止範囲と理由を表示する。オブジェクトキャッシュ・DB最適化は、それぞれの整合性・追跡・資源条件で判定する。TTLなし・変更時全パージを維持し、保存可否の不明を短いTTLで代替する仕様へ変更しない。

初期の保存対象候補は、受入済みコード構成の匿名GET・HEADで、共有可能であり、依存を追跡できる完成応答とする。methodだけで保存を許可しない。初期は正常な公開HTML等に対象を絞り、redirect、404、REST等は個別に検証して追加する。これらをキャッシュしないことは、WP機能の不提供を意味しない。

以下は共有保存しない。

- Authorization、認証・セッション・個人別Cookie、nonce、プレビュー、パスワード保護の解除等に依存するもの。
- Set-Cookie、private・no-store、保存禁止のWP設定・定数・filter等を持つもの。
- 時刻、乱数、外部API、未追跡ファイル、実行時副作用等に依存し、期限なしでの再利用を説明できないもの。
- レスポンス生成中にDB書込み、失効、コード・設定変更が起きたもの。
- 追跡・依存・役割を確認できないもの。

Cookieの有無だけでなく、受入れたコード構成と要求・応答の契約から判定する。匿名GETでDBを書き換える拡張もあるため、明示的に副作用のない経路として検証できたものから有効にする。キャッシュが副作用を省略することによる差分を受入条件へ含める。

閲覧ごとのDB更新が必要な経路は、保存時だけでなく、ヒット応答を返す前の適格性判定でも除外する。キャッシュヒットによって必要な書込み自体を省略しない。書込みの必要性を判断できない場合は、採用済みの判定不能時A案に従い、通常のPHP実行へ回す。

### 4.4 キーとHTTP

キーにはsite、検証済みHost、元のpathとquery、表現を変える受入済みheader・locale等、コード・設定版、失効番号を含める。queryの順序、重複、空値、percent encodingを、同等性を確認せず統合しない。

Varyで示された依存を扱えない場合は保存しない。秘密を含むqueryはキーを含む通常ログへ残さず、共有対象から除く。GETとHEADは、WPの処理差と副作用がないことを確認した経路だけで共通化する。

ETag・Last-Modified・条件付き要求・Rangeは、実際の表現と現在の失効状態に対応させる。古いETagによる304も古いデータの再利用を許すため、bodyと同じ失効検査を適用する。

TTLなしは内部保存の保持方針であり、ブラウザー・CDNへ無期限のmax-ageを返す意味ではない。外部HTTPキャッシュの制御は別に定める。[HTTPキャッシュ標準](https://www.rfc-editor.org/rfc/rfc9111.html)

### 4.5 同時ミスと失効

同じ適格キーの同時生成はまとめる候補とするが、個別のCookie、認可、副作用を持つ要求は共有しない。待機中の期限と失効を再確認し、古い生成者の結果を新しい世代へ登録しない。

DB・コード・設定・メディア等の対象変更時は、応答キャッシュの全キー・全GET変種を失効させる。番号切替による論理無効化と、メモリの物理回収を分離する。object層と内部索引の処理は各契約に従い、応答の全パージだけで最新性を回復したとはしない。

複数プロセスは中央失効番号と利用許可の期限を確認する。通知は高速化の補助とし、通知受信だけを整合性の正本にしない。中央状態へ到達できなければ、共有キャッシュと内部索引を停止する。

## 5 変更追跡と整合性

### 5.1 状態

| 状態 | 高速経路 | 動的な通常処理 |
| --- | --- | --- |
| Initializing | 停止 | 正本DBを使う |
| Building | 停止 | 正本DBを使う |
| CatchingUp | 停止 | 正本DBを使う |
| Healthy | 検証済み範囲で許可 | 利用可能 |
| Suspended | 全失効して停止 | 正本DBが正常なら利用可能 |
| Rebuilding | 停止 | 正本DBが正常なら利用可能 |
| SourceUnknown | 停止 | 対象DBを同定できるまで依存要求を失敗させる |

通常処理への復帰はphp-wasmと正本DBを使う。この経路もDB障害なら失敗を明示し、非公開化の期限を超えて古い応答を配信し続ける代替は初期案に含めない。

### 5.2 自身の書込み

書込み開始をRust経路で把握し、関連する共有高速経路の生成・保存を抑止する。session単位の未確定変更と、site単位の失効状態を追跡する。autocommit、明示transaction、DDL、結果不明を区別する。

確定COMMIT後は失効番号を進め、元の応答生成を再登録させない。変更追跡が当該COMMIT以後のbarrierへ到達し、内部データが整合した後に共有経路を復帰する。COMMITとbinlog位置の対応付けはDB版・接続方式ごとに実証する。対応できない間は最適化を停止したまま正本を使い、架空の位置で再開しない。

rollback時も、拡張が発行したキャッシュ操作や外部副作用までDBと一緒にrollbackされたとはしない。WPによるキャッシュ操作の順序を保持し、transaction中の共有値の可視性を比較する。安全な共有を確認できないtransactionでは、要求内の処理と正本DBを優先する。

### 5.3 外部更新

source identity、対応schema、整合snapshotと開始位置を対応させ、行ベースbinlogをCOMMIT単位で適用する。未確定transactionを内部データや公開応答へ出さない。位置、重複、rotation、ログ消失、source切替、DDLを検査する。

監視接続が生きていることと、変更反映が追い付いていることを区別する。DB側の観測位置と反映位置、取得時刻、sourceの同一性を合わせて利用許可を判定する。位置の観測自体に競合があるため、瞬間の最新性証明とはしない。

外部変更からキャッシュ停止・反映までには遅延がある。次の値を製品条件として決めるまでは、本番の期限なし共有を有効にしない。

| 項目 | 決める内容 |
| --- | --- |
| 外部変更の許容反映時間 | 通常更新を何秒以内に反映するか |
| 非公開化・削除の期限 | 新規配信開始を止める最大時間 |
| 監視異常の検出時間 | 最後の整合確認から何秒で共有利用を停止するか |
| プロセス間失効の期限 | 各HTTP・workerで旧値を利用できなくする時間 |
| 期限超過時の応答 | 正本で再実行、または依存要求を失敗させる条件 |

送信済みbytesや閲覧者が保存したコピーの回収は期限の保証対象から分ける。既に開始した長い応答、browserの再利用、任意CDNを含む撤回範囲を明示する。

### 5.4 checkpointと再構築

checkpointにはsource identity、schemaと接続profile、整合を確認した適用位置、内部データ版、code・codec版を対応付ける。内部データと位置の片方だけ新しい状態を復帰に使わない。

初期は再起動時にキャッシュ・索引を破棄し、fresh snapshotから再構築できる方式を優先する。位置を保存しただけで途中のRAMデータを復元できるとはしない。永続索引や増分再開を追加する場合は、データと位置の原子的な保存を別途実装する。

ログが残れば検証済み位置から再開し、欠落していれば再snapshotへ進む。別source・復元されたDB・古いcheckpointの再利用を検出し、旧コードや旧索引から非公開情報を再露出させない。

## 6 自動資源管理

管理者の固定キャッシュ容量設定は設けない。環境制限、可視範囲の使用量、PHPのWasmメモリ・Rust実行ホスト・DBの配置、生成中の値と新旧更新の余裕を観測し、自動配分する。

概念上の配分は次とする。固定比率や周期の採用値ではない。

```text
共通資源範囲の予算
  = 観測できる実効上限
    - 基盤と通常実行に必要な量
    - 変動と観測誤差への余裕
    - 更新や再構築で予約した量

配分先
  = 応答キャッシュ + オブジェクトキャッシュ + 内部データ
    + 索引 + 構築中領域 + PHPワーカーの追加分
```

同じcgroupや親制限に属するプロセスへ空き容量を二重配分しない。別ホストのDBメモリをローカル予算へ合算しない。外祖先や共有範囲を観測できないときは「不明」を表示し、無制限の拡大を行わない。

圧迫時は新規構築・共有保存・追加workerを抑え、使用効果の低い派生物を退避する。基盤実行の余裕も失う場合は新規要求を制限し、有限の待機後に失敗を返す。キャッシュを消すだけでPHPのWasmメモリやRust実行ホストのRSS問題が解決したとしない。

復帰には余裕の継続観測を要求し、停止と再拡大の頻繁な往復を抑える。更新に必要な一時二重起動の余裕がなければ更新を延期し、理由を表示する。

## 7 php-wasm実行管理

**決定 2026-11-01**：実行ホストはB案とし、RustからPHPのWasmを直接実行する。Node.jsは製品の実行依存に含めない。PHPビルド、Wasmエンジン、ABI、ホスト関数はP0の実証で選ぶ。

**同日の決定**：PHP実行の隔離はA案とする。受入済みのテーマ・プラグインは同じ要求のPHP環境でWPコードとともに動かし、標準のフック・global・objectを共有する。隔離はサイト・役割・ワーカー単位とし、プラグイン間の完全隔離は保証しない。拡張単位で別Wasm環境へ分割し、WPの共有状態をすべて言語境界越しに仲介する実装を必須にしない。

一つの拡張によるtrap・timeout等で要求を正常完了できなければ、要求全体を失敗として回収する。個別プラグインだけを確実に停止し、同じ要求の残りを正常継続できるとはしない。原因の特定や自動無効化も、実際に得られた診断に基づく別の処理とする。既に確定したDB変更・外部副作用は別に照合する。

既存のEmscripten・JavaScript向け配布物とRustホストの間で、少なくとも次の契約を確認する。

| 領域 | 実証する内容 |
| --- | --- |
| ビルドとABI | PHPのWasmターゲット、imports・exports、初期化、要求開始・終了、追加runtime依存 |
| PHP入出力 | superglobal、stdin・stdout・stderr、status、複数header・Cookie、upload |
| ファイル | WP・plugin読込み、read-onlyコード、uploads・一時領域、pathと権限 |
| ホスト呼出し | PHPからRustへのDB・cache呼出し、型・binary、再入、期限、取消 |
| 拡張能力 | 必要なPHP extension、外部通信・mail等の許可能力、未対応時の診断 |
| 資源と回収 | Wasmメモリ、CPU、無限loop、ホスト側停止、要求清掃、worker回収 |

Rust直接実行の成立前に一般WP・plugin互換を達成したとは扱わない。既存の独立Wasmtime実験の成功をPHPビルドの成立証明に流用せず、Node.jsやネイティブPHPへの自動的な方式変更も行わない。

### 7.1 ライフサイクル

状態案は `Preparing → Idle → Running → Cleaning → Idle` とし、異常時は `Quarantined → Terminated` へ進む。code_revisionまたはroleが変わる場合は、旧ワーカーを別版へ流用せず排出する。

コンパイル済みモジュールやインスタンスの再利用と、PHP要求内の状態リセットは別に検証する。superglobal、Cookie、出力buffer、header、hook、global、timezone、locale、shutdown callback、一時ファイル、DB handle等の前要求からの残留を検査する。

同時要求数、待機列、実行時間、body、結果、メモリに有限境界を置く。Rust側でworkerとWasm instanceのpoolを管理し、OS process・thread・instanceの関係を実測で固定する。既存のJavaScript向けpool APIは比較資料にとどめ、直接再利用を前提にしない。[PHPProcessManager](https://wordpress.github.io/wordpress-playground/api/universal/class/PHPProcessManager/)

### 7.2 取消と異常

要求期限・client切断時は、PHP実行、内部RPC、DB処理の取消を協調させる。PHPを止めたことだけでDB transactionがrollback済みとは判定しない。更新結果不明ならDB側の確認と共有最適化の抑止を継続する。

無限loop・ホスト呼出し停止・メモリ超過を、実際に回収できる隔離単位で試す。Wasmエンジンの実行中断と、DB・ファイル等のホスト関数の期限・取消を別々に実装する。Wasm側の中断機能だけで、停止したホスト呼出しまで常に回収できるとはしない。

### 7.3 ファイルと外部能力

実行コード・本体接続コードはread-onlyにし、uploadsと一時領域を分離する。uploadsを任意PHPの実行場所にしない。プラグインの導入・更新は本体の管理経路だけがコード束を生成・切替できる。

外向きHTTP、mail、DB、ファイルは別能力とする。DB接続を迂回できるネットワーク機能を無条件に提供しない。一般ネットワークを許す拡張には、DB宛て接続や管理endpointへの到達をホスト側でも制限する。Wasm内の関数名検査だけで迂回防止を保証しない。

cron・予約公開・mail・外部API等の副作用は、対応するWP動作を保持しつつ、起因と再試行を記録する。外部送信までexactly-onceとはしない。公開要求からのPHP実行を許す変更により、これらの起因も再分類する。

## 8 プラグインとテーマの受入れ

### 8.1 専有領域

本体所有のobject-cache接続、db接続、応答キャッシュ、実行入口、失効管理、内部設定・秘密・制御API、コードの有効版を専有領域とする。

標準フックへの登録、custom post type、taxonomy、shortcode、通常REST、通常SQL、wp_cache_*利用を一括禁止しない。標準のwpdb filterや標準API・本体接続経路を保つ拡張は区別する。subclass等を通じてmysqli接続・driver内部を直接操作するものは、採用済みのDB互換方針A案に従って拒否する。

### 8.2 判定区分

| 区分 | 例 | 動作 |
| --- | --- | --- |
| 受入れ可能 | 対応profileの標準API利用で専有領域と衝突しない | 検査済み版を有効化可能 |
| 既知の衝突 | 独自object-cache・db.phpの設置、接続迂回、mysqli handle・driver内部の直接操作、追跡無効化 | 導入・更新・有効化を拒否 |
| 未対応能力 | 未実装のPHP extension、OS process、未対応driver等 | 必要機能を表示して拒否 |
| 判定保留 | 動的取得コード、未知の接続差替え、複合機能等で、具体的な基盤衝突の疑いを解消できない | 有効化を保留し、RP開発者への報告を求める |

**決定 2026-11-01**：具体的な衝突の疑いが検査で解消しない場合はA案を採用し、有効化を保留してRP開発者への報告を求める。追加確認と再判定の流れは第8.6節に定める。単に未検証であることだけで全pluginを保留せず、完全な人手審査制や全pluginのallowlist制にはしない。

上表の判定保留は、本体専有領域との衝突・禁止能力等の受入条件を判断できない場合を指す。応答キャッシュの保存可能性だけが不明な場合は、第4.3節の採用済みA案に従い、応答キャッシュを迂回して受け入れる。他の受入条件に違反する拡張を、キャッシュ迂回によって許可する意味ではない。

### 8.3 対象と時点

通常plugin、MU-plugin、drop-in、theme、child theme、functions.php、追加読込みコードへ同じ専有条件を適用する。MU-pluginは通常のactivation hookだけでは捕捉できない。[公式MU-plugin仕様](https://developer.wordpress.org/advanced-administration/plugins/mu-plugins/)

検査時点は移行、upload、download、導入、有効化、更新、復元、起動、コード変更検知とする。WP管理画面、CLI、移行ツール、直接配置の入口を別々の抜け道にしない。

### 8.4 導入手順

1. コードを実行しない隔離領域へ取得し、archive構造、path、symlink、サイズ、実際のhashを確認する。
2. 要求するWP・PHP版、extension、ファイル、ルート、DDL、外部能力、専有領域の置換を診断する。
3. 既知の衝突なら、plugin識別子・版・理由・本体代替機能・必要な移行手順を表示して拒否する。具体的な衝突の疑いが解消しなければ、実行前に有効化を保留し、RP開発者への報告を求める。
4. 必要な動的確認は使い捨てDB・隔離workerで行い、本番DB・秘密・外部副作用へ到達させない。
5. 検査対象のhashとpolicy版を固定してコード束へ登録する。
6. 許可されたactivation処理とDDLを管理経路で実行する。失敗時のDB変更を確認する。
7. 新しいコード束へ切り替え、worker排出とキャッシュ全失効を行う。

**決定 2026-11-01**：複合プラグインはA案を採用し、一部に本体との衝突機能を含むことが判明した場合、初回はプラグイン全体の導入・更新・有効化を拒否する。設定off、無効化構成の検証、profile固定による例外受入れは初回には設けない。衝突しない機能もそのプラグインでは利用できないこと、本体の代替機能、別プラグインへの置換候補を案内する。

判定誤りの修正や、衝突機能が除去された新版の受入れは再検査できる。衝突の有無自体が不明な場合は、既知衝突として断定せず、第8.6節の保留・報告を適用する。

### 8.5 防止と検出の限界

静的解析で任意PHPの振る舞いを完全に判定するとはしない。動的試験も全branchの不存在証明ではない。専有領域への書込み、DB宛て通信、内部APIを実行環境でも制限する。

同じPHP要求内の任意コードは、関数やglobalを書き換えて他のコードへ干渉し得る。ファイル・ネットワークの保護だけでPHP内の完全な改変防止を保証しない。接続口の検査・到達経路の制約・受入済みコードへの信頼を組み合わせる。保護が成立しない環境では対象pluginを受け入れず、警告だけで継続する迂回設定を初期案に置かない。

採用した隔離A案はこの共有を許容するが、本体専有領域への侵入や別サイト・別役割への到達を許可するものではない。プラグイン単位の完全な隔離を提供しないことと、ワーカー単位の能力制限・要求間の清掃を実施することを区別する。

### 8.6 保留時の報告と再判定

保留画面とCLIは、疑われる専有領域、検査で確認できた事実、確認できない点を区別し、「RP開発者へ報告してください」と案内する。対象版を有効化するための調査として、報告用資料の生成・内容確認・提出手順を提供する。報告を行わない場合も保留を維持し、警告の承認だけで有効化できる解除操作は設けない。

報告用資料は次を含む案とする。

| 項目 | 内容 |
| --- | --- |
| 製品と環境 | RP・WP・PHP・php-wasm・host・DBの版、必要な能力profile |
| 拡張の識別 | pluginまたはthemeの識別子、版、内容hash、関連拡張の識別情報 |
| 判定 | policy版、検査項目ID、具体的な衝突の疑い、理由、再現操作 |
| 検査結果 | 必要な範囲の診断、実行の有無、判定が保留になった段階 |
| 相関 | ローカル診断ID、提出後に取得した受付番号があればその対応 |

raw SQL、DB内容、資格情報、Cookie、個人情報、絶対path、独自pluginのソース全体を既定の報告用資料へ入れない。理由文へ例外や入力をそのまま埋め込まず、提出内容を利用者が確認できるようにする。製品による自動送信は行わず、利用者による提出操作または診断資料の書出しを経由する。追加のソース・再現データが必要な場合は、その範囲と提出方法を別に案内する。

**決定 2026-11-01**：報告窓口はA案を採用し、通常の互換性報告をRP公式リポジトリのGitHub Issuesで受け付ける。秘密情報を除いた診断と報告文を製品が生成し、利用者が確認して自分で投稿する。製品からの自動投稿、GitHub token・アカウントの製品登録、専用の非公開受付サービスは初期機能に含めない。

設計上の投稿先は、現在のgit originに対応する [RecastPress Issues](https://github.com/KANIKAMA-TTV/RecastPress/issues) とする。配布前に受付URL・公開設定・Issue作成可否を確認し、製品の報告先設定へ固定する。通常の互換性報告は公開可能な情報だけを扱い、秘密を含む再現データを公開Issueへの提出条件にしない。

報告画面・CLIは本文の確認、コピーまたは書出し、受付ページへの案内を提供する。本文や機密をURL queryへ自動埋込みせず、投稿の操作は利用者が行う。受付へ到達できない場合は資料を保持して後で提出できるようにし、報告済みとは表示しない。投稿後のIssue番号・URLを記録できる案とし、記録しただけで保留を解除しない。

報告の案内は、個別サポートの提供、返答期限、対応成功を保証する意味ではない。GitHubの運用設定と本文の形式は実装・配布準備で確認する。

RP開発者の調査結果は、既知衝突としての拒否、誤検出の修正、対応profileの追加、RP側の修正、拡張側の修正依頼等へ分類する。報告受付だけでは保留を解除しない。対象のhash・版と、更新したpolicy・profile・本体版を対応付けて再検査し、受入れ可能と判定された場合だけ有効化を許可する。別版の受入結果を流用しない。

profileの追加や再判定でも、判明した衝突機能を設定offにするだけの複合plugin受入れを初回へ持ち込まない。初回の全体拒否方針を守り、誤検出の解消または衝突そのものが解消したコード版を対象に判定する。

更新候補が保留になった場合は候補を実行せず、正常な既存版を保持する案とする。移行・新規導入では保留中の拡張を実行しない。起動後の変更で保留相当の疑いを検知した場合の停止範囲は、対象と依存を特定して決め、状態と理由を表示する。

## 9 認証と独自SSO

標準のパスワード、Cookie、権限、nonce、ログイン・回復の処理はPHP側WPを正本とする。Rustの既存認証部品を、そのまま別の認証正本として並行稼働させない。

独自設定・導入・更新・パージ等のRust管理APIには、WPの認可済み操作と結び付いた期限付きの内部権限を使う案とする。単なるログイン成功では導入権限を与えず、WP capabilityの対応を固定する。

OIDCは元案の全ユーザー向け標準・初期off・3モード・OIDC限定・MFA非実装を引き継ぐ。一度限りのパスワード許可は連携専用とし、通常WP sessionと同じ権限を与えない。許可の原子的な消費、期限内再開、失効・回復、復元による再発行防止を独自の永続状態へ実装する。

SSO・ログイン・回復・認証済み表示は共有応答キャッシュへ入れない。本体SSOと認証を置換するpluginの衝突範囲は、キャッシュ・DBと別に定義する。

## 10 更新と復旧

**決定 2026-11-01**：同梱基盤の更新はA案を採用する。Rust本体、同梱WPコード、php-wasm、実行ホスト、本体接続コードを、一つの検証済みRPリリースとして管理する。契約版・依存・成果物hash・DB schema互換範囲を対応付け、RP開発者が各部品の修正の取込み・組合せ検証・配布を担う。

利用者が同梱部品だけを独立に更新する経路は提供しない。WP標準のコア自動更新・手動更新やコードの直接配置によって、RPが固定する組合せを迂回できないようにする。管理画面・CLIでの同梱WP更新の案内はRPの更新経路へ統一し、更新可否・保守状態を隠さない。WP互換基準版を変更する場合は、対象版・比較結果・差分をRPリリースで明示する。

一体管理はすべての更新を無条件に自動適用する決定ではない。自動適用する版の範囲、適用時刻、検査、停止・延期条件、修正の配布期限は未決として残す。DB schema変更の有無を更新前に判定し、変更ありの適用・復旧は別契約とする。

ホストOS、Docker、外部DBの更新実行は引き続き製品の対象外とし、操作説明・セットアップ支援に限定する。第三者テーマ・pluginの任意更新は同梱基盤の更新と分け、通常の受入れ・衝突検査を通す。製品基盤の更新に合わせて第三者コードまで無検査で更新しない。

新旧の役割一式を一時二重起動し、検査後に新規要求を切り替え、旧側を排出する元方針を引き継ぐ。DB書込み・cron・導入・変更追跡の担当をleaseやfencingで切り替え、同じjobを二系統が実行しないようにする。lease期限だけで古い側が書けなくなったとせず、必要な操作先でfencingを確認する。

バックアップはDB、uploads、コード束、設定、独自状態、暗号鍵の復旧手順を対応させる。稼働中のfile copyだけを一貫backupとはしない。復元後はキャッシュ・索引を破棄し、sourceとschemaを再確認する。

DB schema変更を伴うWP・plugin更新は、コード差戻しだけで復旧可能とはしない。停止、backup、逆変更、別環境復元のどれを使うかを更新単位で決める。RPO・RTO・保持期間・停止上限は製品条件として未決とする。

## 11 診断と利用者への表示

追加1画面とCLIは、設定値、実状態、理由、次の操作を共通の状態から表示する。

| 領域 | 表示する内容 |
| --- | --- |
| DB | 対応版・schema、接続、待機、実行時間、失敗分類。秘密を除いたquery fingerprint |
| 変更追跡 | source、初期化・追従・停止、確認した位置、反映遅延と観測時刻、再構築理由 |
| キャッシュ | 設定on/off、実利用、hit/miss/bypass、失効、論理使用量、停止理由 |
| 資源 | 観測範囲、実RSS、予算、生成中の予約、unknown、縮小・復帰 |
| PHP | 実行版、worker数、待機、timeout、回収・隔離、拡張能力 |
| 拡張 | 検査済み版、拒否・保留理由、本体代替、更新差分 |
| 更新と復旧 | 有効版、検査結果、backup対応、切替状態、復旧に必要な操作 |

SQL本文やraw query stringを通常ログに含めない。詳細調査用の取得を追加する場合は、機密範囲・保存期間・権限を別に定める。未計測を0、unknownを正常、再接続を反映完了と表示しない。

## 12 構成と保存形式の案

| 論理記録 | 主な項目 |
| --- | --- |
| extension_review | 識別子、版、hash、policy版、要求能力、結果、理由、比較profile、診断ID、報告受付番号、再判定履歴 |
| code_bundle | WP・PHP・host・接続版、theme・pluginのhash一覧、schema互換範囲、有効化状態 |
| change_checkpoint | source identity、profile、schema、適用位置、派生データ版、整合確認状態 |
| job | job_id、起因、code版、冪等キー、lease・fence、試行、結果分類 |
| sso_link_procedure | user、許可消費、手続き状態、期限、transaction、失効と復旧情報 |
| audit | actor、操作、対象、結果、版、相関ID。秘密・本文を含めない |

物理table名、独自schemaの配置、暗号化、鍵の保存、ID形式、retentionはP0または各機能の実装前に定める。ここでWPの既存tableへ列追加することを承認しない。
