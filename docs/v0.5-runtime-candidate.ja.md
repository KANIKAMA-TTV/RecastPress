# v0.5の実行ホスト候補と次の縦断試験

2026-11-02。元のv0.5設計を変更せず、P0の実行ホスト部分の観測とP1への準備をまとめる。製品runtimeの採用・配布許可・P0全項目の完了を宣言する文書ではない。

## 実行候補

次のP1縦断試験では、Linux x86_64のCranelift候補を先に使う。LLVMは比較対象として継続し、Wasmer LLVM compilerの独自利用条件を製品へ自動採用しない。

| 項目 | 固定した実物 |
| --- | --- |
| PHP | 8.5.12、source `f4bfae79d5c19028349082f707930cf0951d23b9` |
| PHP側変更 | 固定のFiber・CGI prefork拒否・managed accessの3patch |
| Rust host | Wasmer 7.2.0 / wasmer-wasix 0.702.0 / Cranelift |
| ABI | wasm32、standard EH、shared imported memory。PHP intは実測8B |
| build環境 | Ubuntu 24.04 x86_64、Rust 1.94.0、固定4ツールasset |
| request形 | CGI、完全応答の保持、compile済みModuleをcloneし要求ごとfresh WASI |
| Rust呼出し | private file transport。stdoutをRPCとしてdispatchしない |

Node.js・native PHPへのfallbackは使わない。通常PHPは比較用の基準であり、製品の要求実行経路にはしない。

## 揃った実行契約

| 契約 | 観測 |
| --- | --- |
| 基本PHP・例外・Fiber・pure WP hooks・IO | native基準を維持し、両backendの固定corpusで一致 |
| CGI | GET/Cookie、POST/raw body、404/2 Cookie/7B binaryが両backendで一致 |
| 権限 | readonlyの照会false・実write拒否・17B不変・Permission deniedが同時に一致 |
| host DB/cache呼出し | 同じ3patch CGIでprivate RPC4要求が両backend通過。固定DB行・要求local cacheのみ |
| 異常要求 | incomplete RPCはPHP終了成功でも拒否。次の要求はfresh stateで正常回復 |
| 資源診断 | 両backendで256MiB actual cap・期待OOM・無cap対照、初期1億Wasm points・実Exhausted・正常回復を確認 |

元Git、source/tool/patch/moduleと生JSONの対応は[実行候補の記録](../experiments/php-wasix-managed-access-probe/README.ja.md)を参照する。清掃の根拠は固定caseでのshutdown、EOF、channel終了、memory recycle、typed Globalの保持・drop、owned hostの終了・reapの観測範囲に限る。全資源の即時回収、stack guard/free/reuse、RSS、hostcallの待機上限まで実証したとはしない。

## P1で最初に確認するもの

上流`wpdb`のprepare/get系・insert/update/delete・prefix等をPHP側に残し、所有`db.php`から要求専有のRust DB sessionへ接続する。RustへWP APIを大量移植しない。最初はキャッシュ・索引・binlog最適化を経路へ加えない。

[driver準備案](../experiments/wpdb-rpc-probe/README.ja.md)では、既存binlog実験で固定したmysql_async 0.37.1を縦断候補とする。既存editing DBのSQLx経路は維持する。SQLxのFOUND_ROWS/MULTI_STATEMENTS、SQL入力のUTF-8制約、raw metadata不足を結果値の補正で隠さず、必要な能力制御をdriverの実handshakeに反映する。

最初の比較は、同じ使い捨てMySQL/MariaDBの同じデータで行うnative実wpdbとRust bridgeの小さな縦断にする。SQL/値のbytes、NULL・empty・binary・decimal・big integer、0行metadata、同値UPDATEの0、insert_id・error後状態、transaction/rollbackと次要求の状態分離を含める。native `mysqli` handle/resultへの直接依存は、元A案の拒否対象のままである。

P0は元設計3.1の実行・版・依存・基準・policy・再利用判断を整理する段階であり、三環境はP0で成立候補、P7で正式受入となる。現在の独立hostの絶対workspace参照は、製品の配布経路としては使わない。P1のruntime入力配置と配布時のportable preflightを具体化し、正式運用・配布条件の残件を維持する。
