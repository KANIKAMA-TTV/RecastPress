# RecastPress本体の自動更新と環境の操作説明・セットアップ支援

実装照合（2026-10-30）：本体updater・Rust全役割の二系統切替・永続job引継ぎ・backup復旧は未実装／未実測。既存のprocess内revision、selected-Wasm consumer、固定A/B別process配信はこのR57実装ではない。更新時の追加資源とR52共有予算、スキーマ変更ありの更新方式は残件を維持。[実装照合](implementation-design-reconciliation-2026-10-30.ja.md)参照。

更新日：2026-10-25（日本時間）。D27とD27-01・R40・R56を反映。自動更新はRecastPress本体のみ。その他は操作説明・セットアップ支援。設計段階であり実装・更新試験は未実施。D27-02・R57で、スキーマ変更のない本体更新はRust本体全体を一時的に二重起動して切り替える方式を採用。無停止は保証しない。検証計画は維持し、スキーマ変更がある更新の方式は未決。

## 1. 決定した範囲

**決定（D27・R40）**：RecastPress本体には一般的な自動更新機能を設ける。本体以外のOS、Docker、DB、PHP、HTTP前段等は「操作説明・セットアップ支援」を提供し、これらを実際にアップデートするコードは持たない。更新実行を代行するAPI呼出し・内蔵スクリプト・ジョブも含めない。提供元の自動更新機能を使う設定手順・設定例・確認方法を案内する。更新・再起動・確認・復旧の実施は運用者または提供元が担う。D18の全層自動適用案をこの決定で変更する。

RecastPress本体の更新でも、テーマ・functions.php由来のWasm成果物、SDK、DBスキーマとの互換性とデータ保護を確認する。自動更新の対象版、初期有効状態、適用時間帯、停止・再起動条件、成果物の検証、失敗時の処理は未決。元WordPressの互換基準版を本体更新と連動して自動変更しない。利用者コードのAI再移植や任意プラグインの更新も自動更新に含めない。

## 3. RecastPress本体更新の設計課題

更新対象は配布済みのRecastPress本体と、そのリリースに含まれる製品部品に限定する。コンテナに同梱したライブラリ等が本体リリースとともに変わる場合は、更新前後の内容と影響を表示する。独立したDB・PHP・Docker・ホストOSの更新まで製品が代行したとは表示しない。

更新前の互換検査、整合バックアップの案内または確認、取得元と成果物の検証、適用後の動作確認、失敗状態の表示、差戻し・復元手順を具体化する。不可逆なDB変更を単なるイメージ差戻しで復旧可能とは扱わない。公開サービスやPHPプラグインにホスト管理権限、Dockerソケット、クラウド管理資格情報を渡さない。

残件は本体の自動更新を実行する主体と権限、対象となる修正・メジャー版、既定値、実行時刻、更新通知、ジョブ・Wasm・DBとの混在版契約、バックアップと復旧の条件。D18-01の旧A/B案にはOS・DBの更新が含まれていたため、そのまま現在の未回答質問としては使わず、RecastPress本体だけを対象に再整理する。

### 3.1 確定した更新方式（D27-02・R57）

**決定（2026-10-25）**：D27-02・R57で、スキーマ変更のない本体更新はRust本体全体を一時的に二重起動して切り替える方式を採用。無停止は保証しない。検証計画は維持し、スキーマ変更がある更新の方式は未決。ユーザーの「実証しない」は、直後の訂正「保証しない」を優先する。方式の採用と、将来の検証結果・無停止の保証を区別する。

当初は一時停止許容のAと無停止可能時だけ適用するBを比較し、続いてWasm二世代案を検討した。現在は上記のRust本体全体の方式で決定しており、旧A/Bを再質問しない。本体以外の更新実行コードを持たない境界は維持する。

### 3.2 停止・切替と失敗時の扱い（詳細案・未採用）

更新前に必要な停止範囲と再開条件を計画し、進行中の保存・コメント受付・内部処理を調整する。更新中の受付拒否・再試行・処理済み状態を区別し、完了した書込みを失わず、途中の要求を黙って成功扱いしない。メンテナンス案内・処理の待機／排出・適用後確認の具体的な経路と権限は三環境で検証する。

停止の上限を超えたときの中断・差戻し・復旧と通知は更新計画で扱う。不可逆なデータ変更後の単純なイメージ差戻しは行わず、整合する復旧経路を確認する。上限値・時間帯・自動復旧の条件は未確定。更新のためにPHPを公開要求から起動したり、非公開データや古いキャッシュを応答させたりしない。

### 3.3 スキーマ変更なしのRust本体全体のブルーグリーン切替（D27-02、採用）

**決定と経緯（2026-10-25）**：Wasm二世代のユーザー提案を具体化し、スキーマ変更なしの更新ではRust本体全体を一時的に二重起動して切り替える方式を採用した（R57）。「保証しない」という訂正を反映し、無停止を保証しない。以下の方式のうち、本体二系統が採用事項、切替手順・資源と障害時の扱いは具体化のための詳細案。

| 更新する対象 | 切替案 | 条件と限界 |
| --- | --- | --- |
| テーマ・functions由来のWasmと資産 | 稼働中のBlueを残し、Greenの成果物を検証・ロード・準備してから、ホストが新規要求の参照を切り替える | 対応するホストAPI・設定・資産・公開データの組合せを照合。Wasm二世代だけではネイティブのホスト本体や実行エンジンを更新できない |
| スキーマ変更のないRecastPress本体・同梱エンジン | Rust本体全体を新旧一時二重起動して切り替える（採用）。公開系・管理系等の実行役割一式を対象とする | 役割分離を維持し、入口・権限・混在版・書込み／ジョブ担当を具体化。二系統の常時稼働や別サーバーを必須とはしない。無停止は保証しない |
| スキーマ変更を伴う本体更新 | 本決定の対象外。互換性を保つ追加変更を含めて切替・停止方式を別途決定 | スキーマ変更なしと同じ方式を自動適用しない。DBエンジン自体の更新は操作説明・セットアップ支援のまま |

#### 切替手順の案

1. Blueで配信しながら、認可済み更新処理がGreenの署名・由来・契約・資産を検証する。準備中も本番の書込みやPHP管理ジョブをGreenから二重実行しない。
2. Greenのロード・初期化、公開読取りでの試験描画、必要なAPI・保存先への接続と起動時の整合確認を済ませる。試験は内部の読取り経路で行い、公開要求からビルド・PHPを起動しない。
3. 更新責任を持つ制御が、新規要求の宛先をGreenへ切り替える。各要求にはコード版・契約版・設定／資産・公開データの組合せを固定し、途中で混ぜない。複数公開プロセスでは経路ごとの確認と混在期間の互換性を検証し、全台同時の原子的切替を仮定しない。
4. Blueへの新規受付を止め、処理中の要求を上限時間内で完了させてから解放する。全パージ・非公開化をまたいだ結果は従来の世代検査に従い、旧要求だから古い非公開情報を配信してよいとはしない。

Wasmの「二つ」は二世代の配備単位を意味する案。各世代は並行要求に応じた独立状態のインスタンス群を持てる。全訪問者を単一の可変インスタンスへ押し込めたり、二世代で利用者状態を共有したりしない。Wasmtime候補ではインスタンスはStoreに属するため、要求・世代の寿命に合わせたStoreの解放を設計する。[Component Instance](https://docs.wasmtime.dev/api/wasmtime/component/struct.Instance.html)、[Store](https://docs.wasmtime.dev/api/wasmtime/struct.Store.html)。候補APIの確認であり、エンジン・版の採用や実証ではない。

#### データ・キャッシュ・処理担当

本体二系統は、対応する共有データに対して新旧コードが共存する案を基本候補とする。DBを二つ複製すれば同期なしで切替可能とはしない。管理操作・コメント受付の書込み、スキーマ変更、内部ジョブ・予約公開・メール等の担当を世代間で引き継ぎ、二重実行と失われた書込みを防ぐ契約が必要。新側の事前確認だけで既存セッションやジョブの互換性を証明したとは扱わない。

切替時はR42に従い全パージし、全キャッシュ種類・GET変種で旧版の描画を新しい応答へ流用しない。Wasm／コード版の切替世代と、DB・ファイル変更による失効世代を区別し、切替後もR49の監視不成立時停止を適用する。温めたキャッシュも世代・監視が一致しなければ捨てる。

コードをBlueへ戻す場合も、現在のデータ・権限・非公開化状態を扱えることが条件。古い公開データやキャッシュへの巻戻しは行わず、新版で受けた書込みを失うDB復元を自動の切戻しに含めない。不可逆データ変更後の単純な旧コード切戻しは不可とする案。

#### 資源と推奨する評価順

更新時だけ新旧を並行させる案とし、定常時の資源が常に二倍必要とは扱わない。準備時には新旧のコード・Wasmインスタンス・コンパイル／ロード・処理中要求を含む追加メモリとCPUが必要で、正確な増加量は測定する。R52の容量完全自動に連携してキャッシュを先に縮小し、予算を確保できなければ切替前に保留する。資源不足を無断の停止更新へ置き換えない。

R57の本体二系統切替を実装設計の前提にする。Wasmだけの二世代切替は別の補助案であり、本体更新の方式と混同しない。スキーマ変更を伴う更新の停止許容・自動適用は別途決定する。性能・メモリ量・切替時の継続性は将来の検証対象として残し、無停止を保証しない。

## 4. 対応版とセキュリティ更新の配信終了（D27-01）

**決定（2026-10-25、R56）**：セキュリティアップデートが自動配信される範囲でサポートし、配信が終わったバージョンは強く警告する。これはOSSパッケージの対応版方針であり、R48の個別サポートなしという提供形態を変更しない。

RecastPress本体の配信系列と、外部OS・ミドルウェア・配備先の更新元を対象ごとに区別する。外部の更新実行は提供元の仕組みと運用者が担い、配信状態の表示のために独自の更新実行コードを追加しない。特定の製品・版・サポート年数や、将来のセキュリティ修正の無期限提供をここで約束しない。

## 5. 検証計画

初回の三環境でRecastPress本体の自動更新、適用後の版・機能確認、中断・失敗時の表示と復旧経路を試験する。環境更新の手順は別に、運用者が読み進めて実施できるかを検証する。OS・Docker・DB・PHPの更新をRecastPressが自動実行する試験は計画しない。どの更新についても、実施していない操作や確認できない結果を成功と表示しない。T33へ配信継続・終了・不明、終了後の強い警告、移行時と管理画面の状態整合、自動配信と実際の設定・適用結果の区別を追加する。R57に従いスキーマ変更なしのRust全体の二系統切替を検証する。スキーマ変更ありの方式・停止方針は別途決定後に期待結果を固定する。二系統切替では、Green準備失敗・切替失敗・処理中要求・新旧の混在・書込み／ジョブの単一担当・非互換データ・切戻し後の最新公開状態・全パージ・メモリ不足時の保留をT33・T14・T35で検証する。未実施。
