# コア内部のDB自動最適化と変更検知

実装照合（2026-10-30）：raw DB／限定検索、論理予約付きview／change buffer、snapshot・binlog・rotation／restart等の所有fixtureは存在する。直前全体gateでは８mode各62を実測した履歴があるが、Cookie本体変更後の再実測は未実行。製品の常駐購読・任意SQLのメモリ検索・自動索引・全process予算・反映／撤回期限は未完成。[実装と上位設計](implementation-design-reconciliation-2026-10-30.ja.md)参照。

## 1. 目的と互換性

検索結果キャッシュに未登録の検索も高速化するため、Rustコア内部に再構築可能な検索用データとオンメモリ索引を持つ。DBサーバーの性能設定のチューニングを前提にしない。変更監視に必要なbinlog設定・権限は性能チューニングと区別して配備要件として具体化する。

WP互換DBを正本とし、WPテーブルの名前・列・値の意味を維持する。最適化を理由にストレージエンジンや列構造を変更しない。既存SQL・外部ツールが参照するDBは正本のままとする。この互換性要件は、D08のプラグイン直接SQLの許可、DB直結権限、任意SQLの無条件互換を新たに承認するものではない。

Redis、Kafka、Debezium等を必須依存にせず、Rustコア内の変更購読担当と検索機構で実現する。利用するライブラリ・ログ形式・対応版は後続で決める。

## 2. 内部構成と権限

```text
WP互換DB（編集用の正本）
    ├ 整合スナップショット → 初期データ構築
    └ binlog → コミット済み変更の追跡
                     ↓
           内部データ・検索索引
                     ↓ 検証
             検証済み公開世代
                     ↓
          検索・描画・応答キャッシュ
```

編集・管理用の内部データと公開用データを分離する。下書き・認証情報・非公開設定を公開プロセスへ複製しない。公開プロセスには編集用DBの資格情報やCDC用権限を渡さず、公開要求は検証済み公開世代を参照する。公開要求からPHPを起動しない。

## 3. 自動高速化

| 項目 | 採用仕様 |
| --- | --- |
| 内部データ | 投稿・メタ・分類等の元の値と複数行の関係を保持し、正本から再構築可能とする |
| 基本索引 | 投稿ID、メタキー、分類、公開状態等を対象にする。初期範囲の詳細は後続で確定する |
| 追加索引 | 検索頻度・処理時間・走査量を観測し、効果が見込める条件についてバックグラウンドで自動構築する |
| 検索計画 | コアの検索APIが、利用可能な索引と通常処理から実行経路を選択する |
| 任意SQL | 初期段階では内部索引への自動変換対象にせず、許可されたSQLはDB本来の実行経路を維持する |
| メモリ | データ・索引・構築中領域を含めて容量を自動管理し、全テーブルの常駐を必須にしない |
| 容量不足 | 追加構築を止め、利用効果の低い索引から破棄する。索引なしでも通常処理で動作可能とする |

照合順序、NULLと空文字、重複メタ、型変換、比較、LIKE、並べ替え等の結果を維持する。同等性を保証できない条件は通常処理へ戻す。索引が未構築・構築中の場合も不完全な結果を返さない。公開側の通常処理は検証済み公開世代を使用し、編集用DBへの直接フォールバックを追加しない。

応答キャッシュのR42・R49・R52と資源配分・整合を合わせ、内部データ・索引へ同じ空きメモリを二重配分しない。追加索引の構築・破棄条件、算式、予算配分は未決。応答キャッシュのTTLなし・全パージ要件を変更せず、検索索引の更新と応答キャッシュの失効を別の処理として管理する。

## 4. DB変更検知

binlog購読を標準方式の候補として採用し、対応する行ベースのログと読取権限を配備時に検査する。利用できない環境の代替方式は別途仕様化し、検知できたと仮定して最適化を有効にしない。

- 初期の整合スナップショットとログ開始位置を対応付け、構築中の更新を取りこぼさない。
- 外部接続による更新も追跡し、コア自身の通知だけで外部更新を検知できたとは扱わない。
- 変更をトランザクション単位でまとめ、COMMIT後に内部データへ反映する。ロールバックや途中状態を公開しない。
- コア自身の書き込みでは、操作完了と反映完了を対応付ける。具体的な待機・公開完了条件は後続で定める。
- 処理済みログ位置を記録し、切断後の再開と再構築を判別できるようにする。位置記録と反映の整合、重複イベントの扱いを具体化する。
- DDLを検知した場合は影響する最適化を停止し、構造を検証して再構築する。
- 初期方式ではトリガーを自動設置しない。更新時刻・行数・最大IDだけを完全な変更検知の根拠にしない。

binlogの利用条件、MySQL／MariaDBの形式差、ログ保持・権限・接続先変更等の検査は後続で定める。任意の管理者操作やログ記録の迂回まで追跡可能とは保証せず、追跡を保証できる運用条件を明示する。ファイル・オブジェクト保存先の変更監視は本方式とは別に維持する。

## 5. 整合性と公開

DBへのコミット完了と公開反映完了を区別する。内部データと索引は同じ世代に属し、異なる世代を混在させない。更新の検証が完了してから公開世代を切り替える。

DB・ファイル変更検知時の応答・コンテンツキャッシュ全パージを維持する。全パージだけで最新データへ反映済みとは扱わず、古い世代の生成結果の再登録を拒否する。監視の接続中とログの反映完了も区別する。

外部更新には非同期の反映遅延がある。更新直後から古い応答が一度も出ないとは保証しない。許容時間、最新性を要求する操作の同期条件、非公開化・削除の反映期限と期限を守れない場合の応答は未決として契約化する。

## 6. 障害と復旧

| 状態 | 必須動作 |
| --- | --- |
| 監視切断・追跡不能 | 全パージしてキャッシュの保存・ヒット利用を停止。内部コピーを最新DBとして扱わない |
| ログが残っている | 処理済み位置から再開し、欠落変更と世代の整合を確認して復帰 |
| 必要なログが消失 | 整合スナップショットから再構築 |
| 索引の破損・不一致 | 対象索引を破棄し、通常処理へ戻す |
| メモリ圧迫 | 索引を縮小・停止し、通常処理を継続 |

復帰時はR49に従い整合確認と再全パージを経る。監視プロセスの再起動や接続成功だけでは復帰しない。通常配信には検証済み公開世代を使用する。最新性・公開撤回を満たせない場合の処理は第5節の契約に従い、無期限の旧世代配信を保証しない。

## 7. 検証計画と残件

T44でMySQL／MariaDBそれぞれの通常検索と索引検索の結果一致、外部SQL更新、ロールバック、並行更新、初期構築中の更新、再起動、切断、ログ消失・重複、DDL、メモリ圧迫、公開境界、キャッシュ全パージを検証する。対応DB版と三配備環境の条件を確定して試験する。

性能はキャッシュミス時の検索時間、初回・追加索引の構築時間、メモリ使用量、変更反映遅延、追跡・書き込み側の負荷を測る。製品の自動最適化全体の検索同等性・性能向上は未検証であり、一定倍率の高速化を保証しない。限定lookup／fixtureの比較成功は、その全体保証に広げない。

未決事項：対応DB版・binlog設定／権限／保持要件、監視不能環境の扱い、外部更新と公開撤回の反映期限、初期索引の範囲、自動構築・破棄基準、検索意味論の対応範囲、再構築・世代切替・位置保存の詳細。
